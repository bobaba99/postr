## 1. Symptom

A researcher selects a block, picks a font from the Style tab's menu, and with the menu still focused presses Backspace: the block disappears. She clicks into a text block, types, presses Esc to "get out of the text" as in PowerPoint, then Delete to remove the block: a letter goes instead, the block stays. Esc never deselects anything. ⌘A selects nothing on the poster. ⌘ + arrow, which moves a selected object in PowerPoint for Mac (Ctrl + arrow, PowerPoint's finer nudge on Windows), moves the block a whole half inch, and Shift + arrow, which resizes in PowerPoint, nudges it. She selects two blocks, drags them together, changes her mind and presses ⌘Z: nothing moves.

**The fine nudge's key, checked in Microsoft's own documentation before building** (the design doc marked it `PPT?` and asked for this check; pages read 2026-10-16):
- Microsoft's "Use keyboard shortcuts to create PowerPoint presentations" (support.microsoft.com, the article with PowerPoint for Microsoft 365 and for Mac). Its macOS table, under "Work with objects and text", lists "Move the selected object in the direction of the arrow." with **"Arrow keys or ⌘+Arrow keys"**, and "Resize selected objects." with Shift + arrow keys; Option + Right / Left arrow rotates 15°, as Alt does on Windows. Its Windows tables have no row for moving an object with the arrows (searched: "direction of the arrow" occurs once, in the macOS table; every Ctrl + arrow row there moves the caret or a slide).
- For Windows, Microsoft's archived Office team blog post "Nudging" (learn.microsoft.com, 2004): an arrow key moves the shape; "For more precision, hold down *Ctrl* while you're hitting the arrow keys and you can move pixel by pixel."

So the fine nudge is **⌘ + arrow on a Mac and Ctrl + arrow on Windows**, which is what the design doc expected ("⌘/Ctrl + arrow"). The two halves rest on different evidence: for Windows, Microsoft's "Nudging" post says Ctrl + arrow is the finer step; for the Mac, Microsoft's table lists ⌘ + arrow as a way to move the object and gives no step size, so that ⌘ is the finer step is taken from the Windows Ctrl rule (an inference, INSPECTED; review round 1, R36-3b, re-read here on 2026-10-16: the macOS row says "Arrow keys or ⌘+Arrow keys" and nothing about distance). Shift and Alt / ⌥ + arrow resize and rotate there, which Postr leaves out (§3.4), so they do nothing. Third-party guides that give Control + arrow for PowerPoint 2011 on a Mac were not used (not Microsoft's; Ctrl + arrow is macOS's own Mission Control shortcut by default). The same page lists "Select all objects on a slide." as ⌘+A / Ctrl+A, and "Select an object when the text inside the object is selected." as Esc (both platforms), the K1 and K2 rows.

## 6. Root cause

- **K0 (H1), one guard copied three times.** The editor's key handler (`PosterEditor.tsx:2168-2174`, main) tested `tagName === 'INPUT' || 'TEXTAREA' || getAttribute('contenteditable') === 'true'`; the table's strip and range listeners (`blocks.tsx:697`, `:723`, main) `isContentEditable || INPUT || TEXTAREA`. A `<select>` is none of these, so a key pressed on a focused menu reached the selection. Canvas paste (record 34) already had the right test, `canvasPaste.ts` `isEditing` (INPUT, TEXTAREA, SELECT, editable text): three keyboard guards and one paste guard said two different things about the same focus. This is open-findings' shared cause R4 for OF-11 and the guidelines `<select>`.
- **K1 (H2) and K2 (H3): the features did not exist.**
- **K3 (H4).** `const nudge = e.shiftKey ? 1 : SNAP_GRID` (main `:2200`), with no test of ⌘, Ctrl or Alt: every arrow with them moved ½ in, Shift + anything 0.1 in. The comment called Shift the fine key on purpose ("constraint as feature"), before the design chose PowerPoint's keys.
- **K4 (H5).** `handleGroupMove` / `handleGroupResize` write every pointer move with `setBlocksSilent` (no undo entry) from `groupDragOrigin`, and `handleGroupDragEnd` (main `:1513-1521`) committed `setBlocks(outerBlocksRef.current)`: `withUndo` snapshots the doc as it is at that moment, already dragged, so the step's undo restored the dragged poster. A single block's drag (`useBlockDrag` `onUp`) puts the pre-drag blocks back silently first, then commits; the group path never did.
- **Siblings looked for.** Other key guards: the canvas paste (`useCanvasPaste.ts`, already `isEditing`), the undo keys (`editorHistory.ts` `isTextEntry`: text-like inputs only, so ⌘Z on a focused menu is the editor's undo, as fix 12 decided: not this rule), ⌘P and ⌘/ (no field test: they are meant from fields too), the comments card (`CommentsPanel.tsx:526`, a click filter, not a key guard; the Comments tab is hidden). Other Esc handlers: the slash menu (`RichTextEditor.tsx` `handleKeyDown`, a React handler that cancels the key), the table's menu (`blocks.tsx` `TableContextMenu` and the cell's `onKeyDown`), crop (`CropOverlay.tsx`), every dialog (window listeners), Preview, area comments; most do not cancel the key, and a browser runs a microtask between two listeners of one key, where React commits the state change the first made (record 02's round-7 audit measured it between two dialogs, `ConfirmModal.tsx`; that dialog therefore listens in the capture phase and stops the key), so an Esc handler that ran after the slash menu's could no longer see the menu: hence Esc runs in the capture phase (section 7; the bubble-phase mutant goes red in the browser, section 8). Other drag commits: the crop edge, the column grip and the sliders (fix 12's merge, `holdDragStep`), and a drag of one selected block in a group (`useBlockDrag`'s group path; whether a user can start such a drag inside the group frame, which covers the selection's box, was not measured), already one step each (INSPECTED; fix 12's G0 measures the single drag). Not looked for here, and found by review round 1 (R36-1, section 9): a drag that changes nothing still added an empty step, because the store's `setBlocks` had no check for a change.
- **What it does not explain.** OF-12 (Delete with a table row or column selected by its strip removes the whole table): the strip is a `role="button"` div, not a text field, so no text-field rule covers it (owner, 2026-10-07: advanced table editing is Later). U-10 and its new sibling, WebKit's forward Delete on a focused control deleting the document's selected text (section 8): the engine's default action, not a listener of the editor. Shift + click on an image replacing the selection (section 4, information): the image's pointerdown is left to the canvas, whose click without a drag clears the selection first (`blocks.tsx` BlockFrame; INSPECTED); outside this rule table.

## 7. The change

**The rule table** (`apps/web/src/poster/selectionKeys.ts`, new, its header; bounded-designs §3.4):

| # | When | Then |
|---|---|---|
| K0 | the focus is in a text field: an INPUT, a TEXTAREA, a SELECT or editable text (`isEditing`) | every key is the field's: Delete, the arrows, ⌘D, ⌘A, ⌘C/X/V and Esc's deselect do nothing to blocks |
| K1 | Esc in editable text (a text block, the title, a table cell, the Content box) | leave the text (the element blurred, the document selection in it cleared) and select the sheet's block it was in, if it is not already selected |
| K1 | Esc anywhere else outside a field | deselect |
| K1 | Esc while something open answers it: a dialog (`editorHistory.ts` `dialogOpen`) or an element marked `data-postr-takes-escape` (the slash menu, the block menu, the table's right-click menu, crop); inside an input method's composition | nothing else (the open thing's own Esc runs as before) |
| K2 | ⌘A or Ctrl+A outside text, with or without a selection | select every block but the locked credit mark (`!b.locked`) |
| K3 | an arrow, no modifier | move the selection ½ in (`SNAP_GRID`, 5 units) |
| K3 | ⌘ + arrow on a Mac, Ctrl + arrow elsewhere (`MAC`, read as ⌘P's is) | move it 0.1 in (1 unit) |
| K3 | any other modifier with an arrow (Shift, Alt/⌥, Shift or Alt with the fine key, the other platform's key) | nothing to blocks; the browser's default is left alone (Alt + Left is Back on Windows) |
| K4 | a group move or resize ends | one undo step: the blocks are put back where the drag started, silently, then the dragged blocks committed (`handleGroupDragEnd`, as `useBlockDrag`'s `onUp`); ⌘⇧Z re-applies it |
| K4 | a drag (of the group or of one block), or an arrow, that changes nothing (released where it started, under half a grid step, or pressed at the sheet's edge) | no undo step (the store's `setBlocks` drops a write that changes nothing, as `updateBlock`, `patchDoc` and `removeBlock` did; correction 1, R36-1) |
| — | Delete / Backspace, ⌘D / Ctrl+D | unchanged |
