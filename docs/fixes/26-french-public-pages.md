## 1. Symptom

Not a defect report: an owner decision the product did not meet. On main every public page (`/`, `/about`, `/why-posters`, `/pricing`, `/tools/figure-readability`, `/auth`, `/billing/success`, `/billing/cancel`, the 404), the public header and footer and the phone notice were English only; only the three legal pages had French twins (`/privacy/fr`, `/cookies/fr`, `/terms/fr`). A French URL for any other page (`/about/fr`) answered with the English 404 (`<html lang="en">`, "Page not found."), no page linked to a French version of itself, and a purchase opened Stripe Checkout in whatever language Stripe chose and came back to English pages.

## 2. Hypotheses

Claims about what the change has to touch, each with the prediction that would confirm it.

| id | claim | prediction |
|---|---|---|

## 6. Root cause

Why the decision touched 50 files and not a handful: the product had no idea of a page language. Every public page wrote its English sentences into its JSX (366 string entries, 14 of them list ids, and 11 sentence builders across the pages, the shared chrome and the checker panel, counted from the dictionaries they moved to: `<scratch>/french-runs/dicts.txt`), links were English paths written by hand, the head came from one record per English path, the prerender and the sitemap knew only those records, the API built English result URLs, and the one place that compared paths to a route (the phone notice's exemption) compared to an English path. The legal pages had been translated by copying each page into a second French component, which works for three long documents whose wording is legal text but would have doubled eight page components, the header, the footer and the checker panel.

What this does not explain: the plot checker's engine writing English is a property of a shared module the editor uses as it is, not a missing mechanism; the French page translates its output (`i18n/readabilityWarnings.ts`) rather than changing the engine.

## 7. Fix

**The rule: a page's language is its URL.** The French page is the English path + `/fr` (`/about/fr`, `/tools/figure-readability/fr`), and `/fr` for the landing page, the legal pages' precedent. `/auth` and `/billing/*` follow the same rule, query kept: `/auth/fr?plan=term`, `/billing/success/fr`. Why the path and not a `?lang=fr` query: one rule for every page; the pages that carry a query (`/auth?plan=`) keep it untouched, and code that rebuilds a query (the OAuth and e-mail return addresses build `?plan=` only) cannot drop the language; the API's success and cancel URLs need no query of their own; each French page is its own prerendered file with its own head, which a query cannot have on a static host. No redirect by browser language and no stored preference: a link to a page in one language opens it in that language.

**A — routing and the language core.** `src/i18n/lang.ts`: `Lang`, `Bilingual<T>`, `HTML_LANG` (`en`, `fr-CA`), `BILINGUAL_PATHS`, `langFromPath` (any case, as the router matches), `englishPath`, `localizedPath(path, lang)` (an English-only path, the editor or the dashboard, is returned as it is), `counterpartPath(pathname, search, hash)`, `useLang()`, `formatNumber` (a decimal comma in French). `routes.tsx` mounts the same components at `/fr`, `/about/fr`, `/why-posters/fr`, `/pricing/fr`, `/tools/figure-readability/fr`, `/auth/fr`, `/billing/success/fr`, `/billing/cancel/fr`.

**B — the head, the prerender, the sitemap, the host.** `seo/routes.json` gains five static French records and four app records (`/auth/fr` prerendered; `/billing/success/fr`, `/billing/cancel/fr`, `/404/fr`), each `fr-CA`/`fr_CA`, titles 32–57 characters and descriptions 137–160, h1 and copy matching the page (MEASURED by the tests: the checker page's five paragraphs word for word). `PageMeta.alternates` (`seo/siteMeta.ts` `alternatesFor`, `twinPath`): a prerendered page whose twin is prerendered carries `en`, `fr-CA` and `x-default` (English); `useDocumentMeta` keeps three hreflang slots, emptied on a page with none, and `scripts/lib/headTags.mjs` mirrors it (`buildPageMeta(path, record, site, routes)`). `scripts/prerender.mjs` writes each page's fallback links in its language (« Pages de Postr », the French static pages, « Connexion », the twin once). `vercel.json`: rewrites for the two billing twins, `X-Robots-Tag: noindex` on `/auth/fr`. `index.html`'s WebSite `inLanguage` becomes `["en-US", "fr-CA"]`.

**C — the pages and the chrome.** One dictionary per page or feature in `src/i18n/` (`chrome.ts`, `landing.ts`, `about.ts`, `whyPosters.ts`, `pricing.ts`, `auth.ts`, `billing.ts`, `notFound.ts`, `figureReadability.ts`, `readability.ts`), English and French side by side, the French typed with the English object's type; the refund lines became `data/refundCopy.ts` `REFUND_LINES` (EN and FR, `REFUND_LINE` stays the English set the editor's paywall uses). The English copy moved there word for word; the code notes behind the claims moved with it (About's per-milestone sources, the price rules). `components/LanguageLink.tsx` is the « Français » / "English" link (`lang` and `hrefLang` of the language it leads to): at the end of the header's flat row (`xl:`) and of the phone menu, beside the footer's copyright (`<nav aria-label="Language">`, only on a bilingual page), in `/auth`'s legal footer, under the billing pages' links and on the 404 (to the same address in the other language). The pages read `useLang()`; Landing's rotating phrases are keyed by language. `Auth.tsx`: the Terms line (record 24) shows its own language's Terms and Privacy Policy, then the other language's in a `lang` span; Supabase is told to send a French e-mail sign-up's confirmation back to `/auth/fr` (with `?plan=` when one is being bought), and a French Google sign-in back to `/auth/fr?plan=…` when a plan is being bought (with no plan it goes to `/dashboard`, as in English; corrected in review round 1, R1-06); `authErrorMessage` leaves the English page's Supabase text as it was and gives the French page the French line of six known codes or the generic one (Supabase writes only English). `PasswordStrength` takes the language. `MobileNotice` is French on a French page and exempts both checker pages. The plot checker panel (`ReadabilityPanel`, `ReadabilitySizingNote`, `ReadabilityCodeView`'s copy button, `FullCodeModal`, `PrintSizeFields`, the preset names) takes `lang` from the page (the editor passes none and stays English; the panel's existing `lang` prop name is the code's language, so the page's is `uiLang` inside); the scale suffix and the copied banner's second half moved from `readabilityLayout.ts`'s tokens to the dictionary, keyed by layout; `i18n/readabilityWarnings.ts` puts the engine's row names and warnings in French with French numbers (`10,0 po × 7,0 po`). The checker panel is keyed by language on the page, so a switch drops an answer said in the other language and keeps the tab's script and last Check.

**D — checkout in French.** `data/billing.ts createCheckout(sku, lang)` sends `{ sku, lang: 'fr' }` from a French page and `{ sku }` otherwise (the English request is byte for byte as before); `startCheckoutForPlan(plan, lang)`; `apps/api/src/billing.ts`: `req.body.lang === 'fr'` (exactly) → `locale: 'fr-CA'` and the `/fr` result URLs. **`fr-CA`, not the brief's `'fr'`:** Stripe's Checkout locales include `fr-CA` (Canadian French; the installed `stripe` 22.3.2 types list it), the pages are `fr-CA`, and `'fr'` would be France's French; the brief's intent (a French Checkout) holds either way, and switching to `'fr'` is a one-word change if the owner prefers it.
