## 1. Symptom

A researcher presses Layout › Auto-Arrange. On the default 3-column poster it puts the Introduction, Methods and Results headings one above the other in column 1, makes 4 columns of 3, and turns "2. Hypotheses" into "5. Hypotheses". On the welcome poster it also shrinks the body text (36 → 31 pt) and the headings, and one Undo does not bring the poster back (three steps). Pressing it a second time moves the blocks again. Separately: a heading pasted into a column takes the last number wherever it lands, figures are numbered across the columns instead of down them, and Export › Preview poster shows no "Figure N." or "Table N." caption at all.

## 6. Root cause

1. **No single reading order** (H1). `PosterEditor.tsx`'s `headingNumbers` counted headings in array order and `captionNumbers` sorted by top edge then left edge; `export/posterContent.ts` copied both; Auto-Arrange's `packShortestColumnFirst` sorted by top edge then left edge and wrote that array back, so it changed the order the numbers read (INSPECTED, main `autoLayout.ts:306`, `PosterEditor.tsx:1487-1497, 1526-1546`).
2. **Auto-Arrange's own rules** (H2): it tried 1 to 5 columns and kept the shortest pack (columns changed), a heading pulled the next block into its column (headings stacked when the next block went elsewhere), and a second pass scaled body and heading text, applied as `setBlocks` plus two `setStyle` calls (three undo steps) (INSPECTED, main `autoLayout.ts:148-255, 309-336`; `PosterEditor.tsx:2075-2081`).
3. **The preview** (H3) is the same cause in one more place: the numbers were computed in the editor and handed to the preview only for headings.

What it does not explain: the stacking of headings at a column's foot under the new function (section 10) is a different matter: the approved function keeps order, not headings with their text.

## 7. The change

**A. One reading order** (`readingOrder.ts`), the design doc's §3.5 A:

| Step | Rule |
|---|---|
| Which blocks | Every block except the title, the authors block and logos (the credit mark is a logo). |
| Columns | A block's left edge within 3 in of a column's leftmost left edge is in that column; columns left to right. |
| Wide blocks | A block at least 90 % as wide as the space inside the margins is a band of its own; wide blocks split the poster into bands, by top edge. |
| Order | Bands top to bottom; in a band, columns left to right; in a column, top edge first. |
| Numbers | Headings, figures (images and charts, one sequence) and tables, each counted in that order, in the editor (canvas and preview) and the PPTX and LaTeX exports (`numberBlocks`). |

It gives the order the templates' authors wrote on all 6 layouts and their portrait versions (TESTED, `readingOrder.test.ts`). After Auto-Arrange there are no wide blocks, so the order is plain column-major.

**B. Auto-Arrange** (`autoLayout.ts`, `arrangeColumns.ts`, `arrangeMeasure.ts`), the prototype's function:

| Step | Rule |
|---|---|
| Fixed | The sheet, 1 in margins, 0.6 in gaps, every font size, the reading order; the title, the authors block and logos stay where they are. |
| Header | The title and the authors block whose top edge is in the top half of the sheet, and logos that start above their drawn bottom. (Review round 1, B-R1: it was every title and authors block, wherever it sat.) |
| Footer | A title or authors block whose top edge is in the bottom half of the sheet (authors and affiliations along the foot): the body ends 0.6 in above it. (B-R1.) |
| Columns | k = the poster's columns now (the left-edge rule above), except that a column of one block that starts inside the column to its left (left of the right edge of every block there: a block dragged part-way across) counts in that column, for k and for "moved". Unchanged, unless the search leaves a column empty. (B-R2.) |
| Body | From 0.6 in under the header's drawn bottom to the bottom margin, or to 0.6 in above a footer. |
| Chosen | The cut points of the reading order into k consecutive columns (a block may move to the next or previous column; a column may be empty, as in the prototype) and the widths, each between max(0.6 × equal, a 40-character body line, the widest table's minimum) and 1.6 × equal, summing to the body width; on a ¼ in grid (½ in for 4+ columns), the last column taking the rest; equal widths always tried. |
| Refined | (B-R3; 2 to 4 columns.) Then every width set whose first k − 1 widths are within ±0.5 in of the centre's, in 0.05 in steps (the first column's offset outermost, the last column taking the rest, every width inside the bounds), each with its own best cut points; a lower F than the grid's choice wins, a tie keeps it. The centre: the grid's (or equal) width set with the lowest score leaving out the keep term, 1000·O + U + 2·Σ\|w − w̄\| (B-R7: it does not depend on where the blocks are now). |
| Heights | Each block's own drawn frame, copied and laid out on the sheet at each width (text at its fixed size; a table wrapping its cells; a figure's image area scaled with the width, its caption wrapping); the refinement's widths measured in a second pass. |
| Score | F = 1000·O + U + 8·moved + 2·Σ\|w − w̄\|, O = Σ w_c·max(0, H_c − H_b) (in²), U = Σ (H_b − H_c)²; for each width set an exact dynamic program over the cut points; the lowest F wins, the first found on a tie. |
| Place | Every block takes its column's width, 0.6 in apart; a figure's stored height is its image area at its stored width, exactly (not rounded: B-R7); other positions and sizes to 0.01 units. |
| Overflow | Kept. Issues: "The columns run X in² past the bottom margin, 1 in from the bottom edge. Shorten some text or make a figure smaller." (from 0.05 in²; live, per column: the widest block reaching past the margin times how far the lowest reaches, as drawn). A column that runs into a footer shows in Issues as overlapping blocks. |
| Credit mark | Moved to the nearest free spot (`ackPlacement.ts`) only when an arranged block now covers it; with none free it stays. |
| Undo | One `setBlocks`, one step; no block moving more than 0.1 units (0.01 in), no step (B-R7). |

**Why this shape.** The search is the prototype's code, ported line for line (the same inches, `toFixed(3)` keys, grid, loop order and tie rule), so G8 can hold it to the prototype exactly. Beyond the prototype only what the editor needs: 1 column (the body's width) and 5 or more columns (the same nested search, equal widths past 20,000 width sets, a bound on a click's time), the header taken as drawn, the credit mark, and the measurement. Since review round 1, also the footer, the lone-block column rule and the refinement (section 9). The refinement departs from the prototype's function: line breaks fall between ¼ in steps, so the grid alone leaves area past the margin that a width 0.05 in away removes, and the owner's words are "as long as we find the minimal area overflow ... just finding the minimal is okay". It is local, not the whole 0.05 in grid, which would mean measuring about 290 widths on a 48 in sheet and searching 53,511 width sets; ±0.5 in, because ±0.25 in left Firefox's welcome poster at 30.90 in² where the whole grid's least is 24.63, and ±0.5 in reached it (MEASURED with the app's heights, the harness's `--fine` read, section 9). Its centre leaves out the keep term so that a second press searches the same width sets as the first: then the first press's layout stays the best, given the same heights (for any block, a move from where it was to the first press's column and on to another costs at least the move straight to that other column, so a layout's F on the second press is at least its F on the first less the first's moves, and the first's layout scores exactly that; INSPECTED, an argument). Centred on the grid's choice this is not guaranteed, but no case was found (about 3,000 random searches of 4 to 7 blocks in 2 or 3 columns, each pressed twice, a scratch run), so the centre rule rests on the argument, not on a measurement; the unit test holds the property itself (the same widths searched wherever the blocks are now). What did make a second press move (14 blocks on the three-figure poster, MEASURED) was the figures' rounded heights (section 9, B-R7).

**The heights: measured directly, not fitted.** The task allowed a fit h(w) = A/(w − p) + q from two widths; direct measurement at every width the search asks (121 widths on a 48 in 3-column poster, then up to about 70 for the refinement) is exact by construction, and G11 measured its error against the heights drawn after Auto-Arrange: at most 0.015 units (0.0015 in) in Chromium and WebKit, 0.008 units in Firefox after review round 1 (about one layout unit: the engines draw sizes to 1/64 px, Firefox to 1/60 px; before the round it was 0.016 / 0.009, the stored figure height's rounding to 0.01 units, removed by B-R7). A first version laid out one copy per block and width at once; WebKit took 250–330 ms for it. One copy per block, re-laid out at each width, gives the same heights in 59–75 ms (MEASURED, scratch timing in the page, three posters):

| engine | one copy per width (ms) | one copy re-laid out (ms) |
|---|---|---|
| Chromium | 38 / 54 / 90 | 29 / 42 / 43 |
| Firefox | 64 / 85 / 111 | 62 / 71 / 78 |
| WebKit | 250 / 330 / 279 | 60 / 75 / 68 |

(3-column template / three figures / crowded.) Without a layout engine (jsdom: every copy 0 tall) the stored heights stand in, a figure's scaled to the width.

## 10. Limits and follow-ups

What the approved function does that a user may not expect (each on the plan's "Queued by record 28" list):

- **A heading can end a column**, its text at the top of the next: 8 of 16 arranged posters in Chromium after review round 1 (MEASURED, the harness's foot-heading read). Out of the approved function's scope ("page-break rules for headings beyond keeping order").
- **An empty column** (owner question): figures that cannot fit lose least area in the narrowest columns, so the lowest F can leave a column empty: 6 figures on 48 × 24 go into one 13.65 in column, the other (31.75 in) is empty (MEASURED in jsdom on stored heights, unchanged by the refinement; the brute force agrees). The prototype allows it. The drawn poster then shows one column fewer, and a second press would arrange it in that many (review finding B-R10; UNVERIFIED in a browser: no column was left empty on the 17 posters of the harness, three engines).
- **The untouched 3-column template** (owner question): the figure placeholder takes a 23.85 in column between 10.20 and 10.75 in ones (Chromium, after the refinement): U fills columns, and with the template's short sample text only the figure can grow.
- **F weighs, it does not rank:** 1000 per in² past the margin. A layout with a little overflow can beat one that fits when it spreads the white space much more evenly (U is at most about Hb² per column, 26² ≈ 680 in² on a 48 × 36 poster, so at most about 2 in² can be traded; INSPECTED, from F's definition). The reviewer saw no such trade: on its grid the lowest F was also the lowest O in all 13 overflowing runs (UNVERIFIED here). The help text says what Auto-Arrange tries ("to keep blocks from running past the bottom margin and to spread the white space evenly"), not that it finds the least overflow.
- **The refinement is local** (B-R3): ±0.5 in around one centre, in 0.05 in steps, 2 to 4 columns. A better layout further from the centre is not looked for (the whole 0.05 in grid would mean measuring about 290 widths on a 48 in sheet): on the crowded poster it ends 656.20 in² past the margin where the whole grid's least is 652.71 (Chromium, MEASURED, `--fine`); on the welcome, long-text and six-figure posters it reaches the whole grid's least. It departs from the prototype's function on the owner's "finding the minimal": **for the lead and the owner to confirm** (a single change in `arrangeColumns.ts`, `REFINE_RADIUS = 0`, turns it off).
- **Off the ½ in grid** (B-R4): the 0.6 in gaps and the chosen widths put column edges off the ½ in grid (12 of 12 body blocks on the 3-column template), so the first drag after Auto-Arrange snaps a block up to 0.25 in sideways out of line with its column: 2.5 units (0.25 in) for a block of the template's third column dragged straight down 1 in (MEASURED, `dragAfter`, Chromium; 0.5 units before review round 1). The design doc's §3.5 C row 8 ("Everything lands on the grid") does not hold under this function. Later: a drag that keeps a block's left edge when it moves straight down, or column edges on the grid.
- **Time on large 4-column sheets** (B-R5): four columns on 72 × 48 take 538 ms to the new layout in Chromium (the harness's `user-4col-72x48`, read, not gated; 438 ms before review round 1: the centre's and the refinement's search added the rest), over the 300 ms target; the width search is bounded only from 5 columns. The reviewer measured 1196 ms at 100 × 48 and, with the CPU slowed 4×, 335 ms on the largest template (UNVERIFIED here). Later: bound or coarsen the search from 4 columns, or run it off the click's frame.
- **The welcome poster opens with an Issues row** (B-R6): "The columns run 26.2 in² past the bottom margin" before any press (MEASURED, `issueBefore`), true of the shipped seed; after Auto-Arrange 24.4 in² (Chromium). Later: a seed that fits.
- **Out of scope (the task):** shrinking or cropping a figure, a figure spanning columns or narrower than its column (wide bands become one column wide: the 2-Col Wide Figure's Key Results heading 460 → 137 and figure 460 → 318 units, the Billboard's key finding 430 → 239 and figure 460 → 239), changing the number of columns, page-break rules for headings beyond keeping order.
- **A footer, plainly** (B-R1): a title or authors block in the bottom half of the sheet ends the body for every column 0.6 in above it, even when it is narrow or blocks sat below it; a column that still runs into it is listed in Issues as overlapping blocks, not in in² (the in² row is about the bottom margin); logos beside a footer are not part of it.
- **One table wider than 1.6 × an equal column** (B-R9): its minimum applies to every column (the prototype's rule), so no width set is inside the bounds and the columns stay equal; the table is drawn narrower than its minimum. Later: the minimum only for the column holding the table.
- **Not handled:** rotated blocks (placed as if upright); logos below the header inside the body (they stay, and a column may run over them); more than 4 columns past 20,000 width sets (equal widths; not timed in a browser); the credit mark covered when the poster runs past the margin and no spot is free (seen before review round 1 on the welcome poster; after the refinement it is not covered there, Chromium).
- **Borders:** a block is measured with the border it is drawn with when Auto-Arrange is pressed (selected 1.5 px, past the sheet's edge 1.5 px dashed, else 1 px). One that is past the edge before and inside after is measured 1 unit (0.1 in) taller than it is then drawn, which leaves that much more gap under it (INSPECTED; not among the posters measured).
- **The web font** (B-R8, INSPECTED as the reviewer, not reproduced): after an import (`postr.autoArrangeOnLoad`) Auto-Arrange runs right after mount, and nothing waits for the poster's web font (Google Fonts, `display=swap`), so heights could be the fallback font's. Main has the same timing. Later: wait for the font before measuring, with a probe that serves a slow font first.
- **Not measured:** Safari on a real Mac; the import's Auto-Arrange (`postr.autoArrangeOnLoad`, which the claims audit queued as a MEDIUM: a replace-import re-arranges the poster; this record changes what Auto-Arrange does, not when it runs); posters with pasted rich HTML; the poster's own web font (the harness blocks Google Fonts).
- **Found in passing and fixed:** the preview's missing figure and table numbers and captions (H3, G10). **Not fixed:** jsdom tests cannot see the editor's drawn heights change after Auto-Arrange (the ResizeObserver is stubbed), so the Issues tests mount the editor afresh before reading Issues; the browser's observer does this itself (G9, MEASURED).
- **Instruments:** G8 compares with the prototype given the app's own heights, refined by the harness's own solver from the record's rule; G11 is what checks those heights against the browser. The harness's reading order, overlap, header, footer, column and strip-area rules are written from this record, not imported from the app; the 40-character line and table minimum are measured by the harness in the same fonts by the same definition, so a shared misreading of that definition would not show (review round 1's six-figure poster showed one such slip in the harness, now corrected: section 9).
