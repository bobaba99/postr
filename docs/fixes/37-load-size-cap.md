**Source:** record 33's sibling f and its review finding R1-F2 (`docs/fixes/33-text-size.md` §6, §9, §10), queued on PLAN.md's Later list ("Queued by record 33", for the lead and the owner) · **Branch:** `fix/load-size-cap`, off main `2b94b5a` · **Status:** implemented; its one review round (a simple fix: the browser, through the user's entry points; the lead's, on the frozen copy `loadcap-frozen-1`) done: 7 findings, none against the fix's code; the documents corrected, the reviewer's probe folded into the instrument as information, a new poster's starting sizes (R37-1, older than this record, a cause of its own) and a reload inside the autosave's window (R37-6) queued (section 9). ## 1. Symptom

A researcher makes her title large in Style › Typography (or sets a big title and heading and presses A+ a few times), sees "Saved", closes the tab, and opens the poster the next day: the title and heading are back at 101 and 58 pt. Nothing says why. The same happens when she types a small body (12 pt) and presses A+ once: title, heading and authors grow together (235, 134, 84 pt) and come back at 101, 58 and 36 pt. The update toast's "Thanks for refreshing. Your poster reopened as it was last saved." (`components/UpdateAvailableToast.tsx`) and the cancelled checkout's "Your poster is exactly as you left it" (`i18n/billing.ts`) were false for her poster.

## 6. Root cause

**The mechanism** (INSPECTED, `pages/Editor.tsx` at `2b94b5a`, measured in section 4). The load effect calls `hydrateIfEmpty(normalizeSheetSize(normalizeStaleStyles(raw), row))` on every open. `normalizeStaleStyles` replaced any level whose size was above `STYLE_SIZE_CEILING_UNITS` (title 30, heading 14, authors 10, body 10 units) with `DEFAULT_STYLES[level]`. It recognised an old poster by a threshold, and the threshold is a size users reach: the Style tab stores whatever is typed (record 33 §10, "the Style tab's size fields store whatever is typed"), and A+ multiplies every level by the body's ratio (record 33's rule 3), so a level set large, or a body set small, passes a ceiling after a press. The repair is in memory; the next edit's autosave wrote the reset sizes back, so the user's sizes were lost for good once she touched the reopened poster.

**What the ceilings were for** (INSPECTED, git history, 2026-04-09, times −07:00):

| time | commit | what it did |
|---|---|---|
| 00:49 | `853ec1c` | the posters table, `data jsonb not null default '{…}'` with styles title 60, heading 28, authors 22, body 18 units (weights 700 / 700 / 400 / 400, line heights 1.1 / 1.2 / 1.3 / 1.4) and an empty `blocks`; `handle_new_user` inserts a row with that default |
| 01:21 | `7ed46bc` | the client's `DEFAULT_STYLES`: title 24, authors 11, heading 13, body 9 units |
| 01:57 | `cb61591` | `createPoster` inserts `{ user_id }` only: the column default supplies `data` |
| 02:03 | `6d94e01` | `hydrateIfEmpty`: an empty poster gets the 3-column template and the Classic palette, its stored styles kept |
| 02:18 | `4e3190c` | the autosave: from here the client writes the poster back, the old sizes included |
| 02:33 | `9aa4620` | the client's `DEFAULT_STYLES` calibrated to 22 / 8 / 5 / 5 (title / heading / authors / body; today 14 / 8 / 5 / 5) |
| 02:48 | `979df80` | the migration's default rewritten in place to the calibrated sizes, and `normalizeStaleStyles` with the ceilings added: "older documents that were already autosaved before the calibration fix have the broken style sizes baked into their data jsonb" |

So the stale population is posters whose data came from the column default as `853ec1c` wrote it. The client's pre-calibration `DEFAULT_STYLES` (24 / 13 / 11 / 9) were used by one test and by nothing that writes a poster (INSPECTED, `git grep DEFAULT_STYLES 9aa4620^`: `constants.ts` and `autoLayout.test.ts` only); the ceilings would have replaced only their authors (11 > 10) anyway. A poster could hold some of the old sizes and not others only through an edit made by a client older than `979df80`, between 02:18 and 02:48 on 2026-04-09; after `979df80` every open replaced all four old sizes at once (each is above its ceiling) and the next edit wrote all four. Production's Supabase was deferred at the time (`d0b6b4e`, "defer prod Supabase"): whether any production row was ever created with the old default is UNVERIFIED (production is not read in this work).

**Why all four sizes must match** (MEASURED for the title, arithmetic for the rest). Each old value alone is a size a user can type: 432 ÷ 7.2 = 60, 201.6 ÷ 7.2 = 28, 158.4 ÷ 7.2 = 22 and 129.6 ÷ 7.2 = 18 are exact in floating point (node), and RELOADONE stored a title typed as 432 pt as exactly `60` in all three engines. A rule matching one level would reset that title. All four at once is a poster nobody makes by hand, and it is exactly the old default's shape.

**The same pattern elsewhere** (section 4, MEASURED unless said). Every repair the editor applies when it opens a poster, by what it overwrites:

| repair | where | overwrites a value a user set? |
|---|---|---|
| sheet size | `normalizeSheetSize` (`Editor.tsx`) and `setPoster` (`stores/posterStore.ts`), `withUsableSheetSize`: a size outside 3–1000 in or not a number | no: the fields accept 10–100 in (`resizeSheet.ts`); 100 × 10 in kept across a reload (`reload-siblings`, three engines). A size below 3 in can come only from an import (hidden; INSPECTED) |
| palette | `hydrateIfEmpty` only (no other load-time palette write, INSPECTED) | not for a poster with blocks: "Nature / Biology" kept (`reload-siblings`); yes for an emptied poster (next row) |
| font | none: an unknown font falls back where it is drawn (`FONTS[f]?.css ?? f`), the stored value is kept | no: "ZQ Unlisted Sans" kept in the store and asked for by the canvas (`font-not-listed`), and DM Sans kept (`reload-siblings`) |
| an empty poster | `hydrateIfEmpty`: no blocks → the 3-column template and the Classic palette | **yes**: a poster whose blocks were all deleted (no credit mark was placed on either poster tried) reopens with 14 template blocks and the Classic palette (`reload-emptied-…`, three engines) |
| the credit mark | `setPoster` `ensureAckBlock`: adds the mark when absent and there is room; never moves one (INSPECTED) | no |
| stored images | `migrateBase64ToStorage`: a `data:` image uploaded and its source replaced by the stored path (the same image) | no value changes; its use of the load-time blocks is on PLAN's list already |

**The emptied poster is the same pattern, not the same cause.** Both repairs recognise the documents they were written for by a property a user's own poster can also have. For sizes, the documents have their own values (the old default), so the remedy is to recognise them by those values. For the empty poster, the repair reads only whether there are blocks, and a row the database has just created and a poster its user emptied both have none. Their other values are not today's defaults, as this section first said (corrected after review round 1, R37-2): a new row holds the posters table's column default (the migration file's, title 22 units drawn at 158.4 pt, authors line height 1.5, the palette with accent #0f4c75; MEASURED `new-row-defaults`, three engines), and a new poster emptied with "Delete block" in today's editor differs from that row only in its palette, the Classic one `hydrateIfEmpty` laid out and the first save wrote (accent #1a80bb; MEASURED `new-row-emptied`, the one key differing `palette`, three engines). So "the row's data equals the column default" also separates them today. It would not for a poster emptied and saved before the palettes were rebuilt (`c0af001`, 2026-07-28), while Classic was the column default's palette (INSPECTED: the same seven colours from `7ed46bc` to `c0af001^`), with its styles never changed. Each rule (the row never saved, the data equal to the column default, or keeping the palette) needs a decision, outside this record's brief. Measured and queued (section 10).

**What this cause does not explain.** The two round trips 1 to 2 units in the last place off across a reload and around a Style-tab edit (record 33 R1-F3: the anchor is held in the tab; RTRELOAD reads the same misses after this change, section 8); a figure caption's 7.2 pt jumps (its own rounding rule); the share page drawing a poster as stored (it runs no repair); the emptied poster's template and palette (above); a new poster's 158.4 pt title (review round 1, R37-1: the row's data is the column default, which no repair touches; section 10).

## 7. Fix

`apps/web/src/pages/Editor.tsx`: `STYLE_SIZE_CEILING_UNITS` removed; `PRE_CALIBRATION_SIZES` (title 60, heading 28, authors 22, body 18 units, the column default of `853ec1c`, exactly) and `LEVELS` added; `normalizeStaleStyles` tests the four sizes together (`LEVELS.every(... === ...)`) and replaces every level with `DEFAULT_STYLES[level]` when they all match, as the ceilings did for such a poster; a missing level is still filled. The load path's comment and the function's header say the rule. Nothing else changed: no stored data, no other repair, no copy.

**The rule table:**

| # | a stored poster's styles | opened with |
|---|---|---|
| 1 | title, heading, authors and body sizes exactly 60, 28, 22 and 18 units (the old default as a whole) | today's `DEFAULT_STYLES` for all four levels (size, weight, italic, line height, colour, highlight: the whole level, as before) |
| 2 | anything else, however large or small (a size that is not a number included) | every level as stored |
| 3 | a level missing | today's default for that level; the others by rows 1 and 2 |

**Plain behaviour.** The repair stays in memory, as before; the autosave writes it on the next edit. For an old-default poster, its four sizes stored as numbers, the result is the same as before this record (all four ceilings were passed); for every other poster nothing on load touches its sizes. Two odd shapes of the old default that the ceilings also repaired are now drawn as stored (review round 1, R37-5; MEASURED, `old-default-strings` and `old-default-authors-absent`, three engines, and the ceilings served back, `K1-ceilings-back`, Chromium): its sizes stored as strings ("60", "28", "22", "18", before 100.8 / 57.6 / 36 / 36 pt, now drawn at the sheet's fallback, 115.2 / 115.2 / 129.888 / 115.2 pt, the fields reading 432 / 202 / 158 / 130), and the old default with no authors level (before 100.8 / 57.6 / 36 / 36, now 432 / 201.6 / 36 / 129.6, the missing level filled, rule 3). No writer is known for either (INSPECTED: `StyleLevel` has had four levels since `579bc9b`, the typed data model; the column default always held four numbers; the Style tab has stored a number, `+e.target.value`, since the editor's first port, `a8bda67`, and `ptToUnits(+e.target.value)` since `9aa4620`; import is hidden, `IMPORT_ENABLED`).

**Out of scope:** changing what the readability guideline advises (the ceilings were not a guideline the app shows: no copy named them, INSPECTED); enforcing a size anywhere (the Style tab's fields still store what is typed); the share page, imports and version restore (they never ran this repair); the emptied poster's template and palette (a separate cause, section 6).
