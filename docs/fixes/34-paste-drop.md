# Record 34 — Paste and drop on the canvas make blocks; an image pasted into text lands beside it

**Source:** the MVP scope's "paste" (PLAN.md, "MVP scope and the Later list": the editing functions, undo, paste and the rest); the MVP editor design, `docs/launch/mvp-editor/bounded-designs.md` §3.3 table A row 3, table B orders 2 to 5, "Drop" and "Image checks" (order 1, Postr's own copied blocks, is the next fix) · **Branch:** `fix/paste-drop`, off main `c67a3db` · **Status:** implemented; reproduced first from the user's entry with a new committed instrument (`apps/web/scripts/canvas-paste-check.mjs`: a real ⌘V of a real clipboard where the engine allows it, trusted drops in Chromium) in Chromium, Firefox and WebKit on a clean tree of `c67a3db`; changed; the instrument green in the three engines (section 8); 43 of 43 mutants killed and 5 of 5 blind spots guarded in the browser; web suite, tsc and the production build pass; its one review round (a simple feature: the browser, through the user's entry points, on the frozen copy `pastedrop-frozen-1`) found 10 (2 MEDIUM, 6 LOW, 2 INFO): both MEDIUM and two LOW reproduced first in the browser and corrected with a test red first, the other LOW recorded (section 9); after the corrections the instrument is green in the three engines, 50 of 50 mutants killed and 3 of 3 blind spots guarded; the correction is in the frozen copy `pastedrop-frozen-2`.

Evidence labels as in `docs/fixes/README.md`: MEASURED (a number from a re-runnable command), TESTED (a test that fails without the change), INSPECTED (read, nothing ran), UNVERIFIED.

## 1. Symptom

A researcher copies a figure (a screenshot, a picture from a web page), clicks the grey area around the poster and presses ⌘V: nothing happens. She copies a table from Excel and pastes it the same way: nothing. She types in a text block and pastes the figure there, to have it next to the paragraph: nothing, without a word. She drags the figure's file from the Finder onto the poster: nothing is added, and the browser may open the file in place of the editor. And when she does put a picture into a figure block with "+ Upload figure", one ⌘Z leaves an empty frame that draws nothing; it takes three presses to get back.

## 6. Root cause

- **Table B and Drop (H1, H3): the feature did not exist.** No listener on the canvas or the document took a paste whose target is not editable, and no element took a drag carrying files. The editor's paste handlers are each on an editable element: `RichTextEditor.tsx:266` (text blocks, headings, the title), `TableCellEditor.tsx:60` (a cell, record 32), the chart ladder's data box (`DataStep.tsx:214`). `useEditorHistory.ts:119` listens for every paste on the document, in the capture phase, only to mark the next text edit as an undo step of its own (`stores/inputHint.ts` `notePaste`).
- **Table A row 3 (H2).** `RichTextEditor.tsx:266-289` (base) cancels the browser's paste and inserts `pastedHtml(text/html, text/plain)`; with an image alone both are empty, so `insertHTML` inserts nothing.
- **The image block's upload (H4), a sibling on the shared path.** `blocks.tsx:321-353` (base) `handleFile`: `onUpdate({ imageSrc: previewUrl })` (a `blob:` address, a step), then `uploadPosterImage(...).then(storageSrc => onUpdate({ imageSrc: storageSrc }))` (a second step; the preview revoked), and an `Image` loaded from the file → `onUpdate({ h })` (a third). A file `uploadPosterImage` refuses (over 10 MB) went to `readImageFile`, which alerted and returned, so the revoked preview stayed stored. A paste into a selected empty image block and a drop on an image block put a file into that block, so they had to go through this path (the rule: "exactly as the image block's own upload does"); built on it as it was, each would have been three undo steps and could store a dead preview. The cause shared with the new feature is one: a file put into an image block wrote every intermediate state into the poster. The change puts the file in with ONE update after it is stored (section 7).
- **Siblings looked for.** Other ways a file enters a block: the logo's picker (`LogoPicker` → `onPick(imageSrc)`, one update of a stored path: not this defect, INSPECTED), Import's uploads (`pdfImport.ts`, `pptxImport.ts`, `postrFile.ts`: blocks built with their stored paths before the poster is loaded, not undo steps, INSPECTED). Other editable surfaces a paste reaches: the table cell (record 32; an image into a cell stays the browser's, out of scope), the sidebar's fields (`<input>`, `<textarea>`, and the Content box, a `RichTextEditor` the canvas gives no `onPasteImage`: such a paste still does nothing there).
- **What it does not explain.** §3.3 D (an upload overwrites the file a ⌘Z points back to, H5) is the storage layout's, not this path's: it is unchanged and measured (section 8). Why Playwright's Firefox carries no file in a clipboard image paste is the test browser's, not the app's (section 3).

## 7. The change

**The rule table** (`apps/web/src/poster/canvasPaste.ts`, its header; bounded-designs §3.3):

| When | The clipboard holds | Then |
|---|---|---|
| the caret in a text block, a heading or the title (A3) | an image file and no text | a new image block next to that block: to its right, top aligned, ½ in away, if it fits on the sheet there; else ½ in below the text as the canvas draws it, left aligned, kept on the sheet; the text left as it is, the new block selected |
| nothing in edit mode (a block may be selected), order 1 | Postr's own copied blocks | not built: the next fix adds its check first in `readCanvasPaste` |
| order 2 | HTML with a `<table>` and no text around it | a new table block filled by record 32's grid reader (`tablePaste.ts` `htmlTableGrid`, now exported), Insert › Table's borders |
| order 3 | an image file and no text | a new image block; if the one selected block is an EMPTY image block, that block is filled instead |
| order 4 | any other text, tabs included | a new text block holding record 32's cleaned paste (`sanitizeTyped(pastedHtml(…))`) |
| order 5 | anything else | nothing |
| a drop on the canvas | image files | one image block each, the first centred on the drop point (read through the zoom), each next 1 in down and right of the last; one image dropped on an image block, empty or not, goes into it |
| any image | over 10 MB, or not an image | skipped with today's message (the upload's own words, moved from `blocks.tsx` `readImageFile` to `imageFile.ts` `imageFileProblem`) |

"Text" is what a paste of the clipboard into a text block would insert (`canvasPaste.ts` `pastedWords`: record 32's `pastedHtml`, the clipboard's HTML cleaned when it has HTML, else its plain text, kept when it holds words a user would see), the same function for table B's order 3 and order 4 and for table A row 3: an HTML `<img>` alone (a browser's "Copy image") or a style sheet is not text, nor an `<img>` with the image's address as plain text beside it (the HTML wins, as in a text block); the address alone is text. (The first version read "text" from the plain text or the HTML's words for orders 3 and A3 but stored order 4's content from the HTML, so such a clipboard was text to one and empty to the other and pasted nothing: section 9, R34-2.) A paste whose target or focused element is a field, a menu or editable text is the field's; nothing happens while a dialog is open (the feedback dialog is one since section 9's R34-7), while a table shows cells selected by dragging (`cellRangeShown`, the table's `data-postr-cell-range`; section 9, R34-3), in Preview, read-only or reviewing.

**Where a new block goes** (one rule each): a paste with nothing in edit mode centres it in the part of the sheet the canvas shows, snapped to the ½ in grid and kept on the sheet; a drop centres it on the drop point, snapped and kept on the sheet. Size: Insert's for its kind (`insertSize`, which Insert's `addBlock` now reads too: 155 × 140 units for a text, a table or an image); an image's is Insert › Image's box with the image's shape (`imageBlockSize`: a wide image keeps the width, a tall one the height; its height is what the image block's own fit makes of its width, so the fit on load adds no step).

**One undo step.** A new block is made once its file is stored (an image), then all the new blocks go in with one `setBlocks` and are selected (`PosterEditor.tsx` `commitPastedBlocks`), against the poster as it is by then (an edit made meanwhile is kept); nothing is added if another poster was opened meanwhile. Filling or replacing an image block is the block's own upload, `ImageBlock` `putFile`: the checks first; a preview drawn from the file while it is stored, never stored; then ONE update, the stored image and the height its shape gives the block's width (the upload's own fit skipped a change of 2 units or less, as a step of its own; in the one update the height is set to the shape). "+ Upload figure", Replace, a paste into the selected empty block and a drop on the block all go through it (the last two by the `postr:image-file` event, `imageFile.ts` `putFileIntoImageBlock`). Only the file put in last updates the block (`putSeq`): one that comes back after a later one was put in changes nothing, its preview already revoked (section 9, R34-1: it used to land as a step of its own and revoke the later file's preview, so the block drew nothing until a reload). The upload is unchanged: `uploadPosterImage` into the poster owner's folder (`storage://`), a data URL when there is no owner or it fails.
