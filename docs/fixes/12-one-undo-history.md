## 1. Symptom

FINDINGS F2, as reported: "⌘Z in a text block undoes one character at a time; redo never works." What a researcher meets (all MEASURED on main by the item 12 reproducer and confirmer, section 5): ⌘Z with the caret in a text block is the browser's undo, not the editor's. In Chromium it removes one typed character per press; in Firefox and WebKit the whole visit. It crosses blocks (⌘Z in block B undoes block A's typing). Clicking away and pressing ⌘Z then brings back the text just undone, and redo after leaving the block never works. ⌘Z with the caret in text does not undo a font change made a moment before, or bring back a deleted image. In a sidebar field (Authors › Author name, Edit block › Font size, the Content box, the caption, a slider) ⌘Z is again the browser's: it can undo canvas typing instead of the field (60 pt typed in Font size, ⌘Z: 6 pt in Chromium). In the Figure tab's code box, behind a dialog and in the preview, ⌘Z can change the poster unseen. Table cells type backwards ("abc" becomes "cba", 12 of 12 cases) and each keystroke is a step of its own, so 55 characters in a cell push an earlier change out of the history. "Undo" shows when nothing was undone; Ctrl+Shift+Z sent as key "Z" (Windows) does not redo; the history holds 50 steps; there are no Undo/Redo buttons; restoring a version wipes the history. The selection toolbar's A+/A− and alignment buttons change the screen but never reach the poster.

## 6. Root cause

**Two undo histories that never met, chosen by where the focus was** (the reproducer's statement, each link MEASURED by it or the confirmer; INSPECTED here against the code):

1. **Key dispatch.** The only ⌘Z/⌘⇧Z/⌘Y handler stepped aside for INPUT, TEXTAREA and contenteditable targets, and was not installed in preview or acted on while a modal was open. In every one of those states the browser's undo ran instead of the store's.
2. **The browser's undo was stored as an edit.** `RichTextEditor` committed every `input`, `historyUndo` included, and `updateBlock` stored a patch that changed nothing, wiping the redo (U3, U4, U10).
3. **The editor rewrote the DOM under the browser's history, and never under the caret.** A focused editor was never repainted (an undo with the caret inside would have left stale text that the next keystroke wrote back, H4), while every other editor was rewritten from the store on each keystroke — which also made Chromium's undo step one character.
4. **Engine-specific granularity.** The browser's history is per document in Chromium and WebKit and per field for Firefox's inputs, so the same ⌘Z removed one character, a whole visit, or text in another block or field.

The design choice behind 1 was deliberate (FINDINGS F2/F3: text undo was left to the browser to keep the caret), but the store also snapshotted every text change, so the two histories diverged by construction.

**Shared with other findings, and fixed with it here** (same "store → focused editor" sync, or the same key dispatch): the reversed cell typing (S8: `dangerouslySetInnerHTML` rewrote the cell, and React 19 rewrites on every render); the sidebar fields and slider (S1, S2); the code box (S3, from item 7's confirmer); the preview and modals (H10); the Edit-tab caption and note grouping (fix 01's hand-on, the same "group by patch shape" rule as H6).

**What it does not explain** (each its own cause; fixed here only where the owner said so): the case-sensitive key match (H7), the unconditional toast (H8), the 50-step depth (H9), A+/alignment never persisting (H5: no commit, and the sanitizer's allowlist — the owner chose to remove the buttons), version restore wiping the history (it called `setPoster`, the load action), group move/resize not recorded (item 6), Auto-Arrange taking 3 steps, and Enter's line break not being saved (section 10: the sanitizer flattens the `<div>` the browser adds; not undo).

## 7. Fix

**Owner decisions (2026-10-06)**, which set the shape: (1) ONE history for everything that edits the poster: ⌘Z/Ctrl+Z undo and ⌘⇧Z/Ctrl+Shift+Z/⌘Y/Ctrl+Y redo through the editor from every such field, case-insensitively; the browser's undo never runs on the poster; (2) the Figure tab's code box, the poster name, comments, dialogs and the preview keep the browser's undo for their own field and never change the poster; with a dialog or the preview open ⌘Z does not edit the poster; (3) each typed word is one step, and a step also ends at a format change, paste, cut, a deleted selection and Enter; non-text edits keep their grouping; (4) after an undo or redo of text, that block has the focus and the restored text is selected; (5) Undo and Redo buttons, disabled when there is nothing to do, named, reachable by keyboard; (6) restoring a version is one undoable step; (7) nothing shown on an empty history; (8) remove A+/A− and alignment from the selection toolbar; (9) table cells keep the order of typed letters and join the history by word; (10) one depth, 100.

**A. The key router** (`editorHistory.ts`, `useEditorHistory.ts`, replacing the handler in `PosterEditor.tsx`). One keydown listener, in the capture phase on `window`, installed in every state including the preview. `historyKeyAction` matches ⌘ or Ctrl with Z (Shift: redo) or Y, the letter without case, by `code` only when the layout types a letter that is not Latin there (Cyrillic, Greek; Dvorak's ";" on the Z key is not undo, review R1-F5), and never with Alt (AltGr is Ctrl+Alt on Windows; on AZERTY ⌘⇧ and the Z key send key "Z" from code `KeyW`, which the case-insensitive match takes). `routeHistoryKey` decides by the element the key landed on: a text field inside `[data-own-undo]` or inside a dialog keeps the browser's undo (`'own'`); otherwise, with a dialog open (`[role=dialog][aria-modal=true]` or the app's shared modal markup `[data-postr-modal-content]`, not one fading out; the preview overlay is one) the key is cancelled and nothing else happens (`'block'`); everywhere else the key is cancelled and the editor's history runs (`'history'`). "Everywhere else" is everything that edits the poster: canvas text blocks and the title, table cells, the Content box, number fields, sliders, selects, the caption and note, the Authors fields, buttons and the page itself.

**B. The browser's own history** (`historyInputVerdict`, the `beforeinput` listener on the document, capture phase). A `beforeinput` of type historyUndo/historyRedo is allowed only in the field the key was pressed in when that field keeps its own undo; any other is cancelled — the per-document history of Chromium and WebKit aiming a code box's ⌘Z at a canvas block, a press the editor already handled (so one ⌘Z is one step even if an engine fires its own input too). With no key press in the task (the browser's Edit menu or a context menu) it is cancelled and, with the focus in the poster and no dialog open, routed to the editor's history; in a field that keeps its own undo it is that field's. An `input` of those types is never stored — the path an engine takes when it fires no `beforeinput` (Firefox's Edit menu with the focus on the page; Chromium's and Firefox's `execCommand('undo')`, E5, E5i): the text editors refuse it and put the field back to the store's value with the caret kept (`useEditableHistory.commitInput`); for a sidebar `<input>` or `<textarea>`, which has no editor component, the document's `input` listener notes it, the store stores nothing in that task (`withUndo`), and React puts the controlled field back to the poster's value when its change is refused (review R1-F3). A key pressed next starts a new record (`resetInputHint`): a browser may run a keystroke queued during a long task before that task's end-of-task timer, and the stale record would refuse it.

**C. Steps** (`historySteps.ts`, `inputHint.ts`, `posterStore.ts`). The definition of a word step, precisely: within one text field — a block's content, one table cell (`cell:<block id>:<index>`), a caption, a note, or the one string a keyed sidebar edit changes (an author's name, an institution's city) — an edit is classified first from what the browser said about it in that task (`inputHint.ts`, noted by the document's listeners in the capture phase, before any field's own handler, and dropped at the end of the task or at the next key), then from the field's plain text before and after (`classifyTextEdit`). A **paste** (the `paste` event), a **drop** (`beforeinput` of type insertFrom…), a **cut** or a **deleted selection** (`beforeinput` delete… over a selection) is a step of its own, even of one character. One character inserted is **typing**, and it starts a new step when it is not whitespace and the character before the caret, read at `beforeinput`, is whitespace or there is none (the space stays with the word before it: " hello world" is the steps " ", "hello ", "world"; "d" typed in front of "dog" after "the " starts a word, though the text alone reads it as a second "d" inside "dog", review R1-F6); where the caret is not known, the character before the insertion the text diff finds decides. A character typed over a selection starts a new step that the following letters join (the browser's `beforeinput` says a selection was replaced, where the text alone would read "Jane Doe" → "J" as a deletion). A **composition** (an input method for Japanese, Chinese or Korean, a dead key, a phone keyboard that composes each word; review round 2, R2-F1) is typed as one unit: from its `compositionstart`, every edit it makes — each update (`beforeinput` of type insertCompositionText, over the selection the browser keeps on the text composed so far) and its commit (the same type in Chromium; `deleteCompositionText` then `insertFromComposition` in the Input Events Level 2 draft WebKit follows) — joins one step. Whether that step is new is decided once, from the caret at `compositionstart`: a new step when the composition replaces a selection, or when the character before it is a space, the start of the field (or not known), or a Han, Hiragana or Katakana character, their punctuation or a full-width form (scripts written without spaces between words, where each composed phrase is a word); after any other character it continues the word being typed (a Korean syllable after another, "é" composed after "caf"). So " 日本語" is the steps " " and "日本語"; "中文很" typed after a space is " ", "中", "文", "很"; " 한글" is " " and "한글"; " café" is " " and "café". A key released inside a composition (an input method's candidate list read with the arrow keys) does not end the step. One character removed is a **deletion**, and deletions in a row are one step; anything else — a newline, a format change (the text unchanged, the markup not), a longer change — is a step of its own. Typing and deleting never join each other; a pause never splits a word. A keyed sidebar string (an author's name) is text only when the browser reported typing, deleting or a paste in that task: a colour is a string that a picker changes one hex digit at a time ("#112233" → "#112234" reads as a typed letter), and a colour input fires no `beforeinput` (review R1-F1). The editors also end a step when the caret moves by a click or an arrow key, and focus entering a field ends one (`focusin`). Edits that are not text keep their grouping: number fields, sliders and colour pickers merge keyed bursts within 600 ms / 5 s, clicks are a step each, and the caption-spacing slider stays one step per change (unchanged). `updateBlock` adds no step for a patch that changes nothing (U10). `undo()` and `redo()` return whether a step was applied. `UNDO_HISTORY_LIMIT` is 100 for both stacks, and the About page says "Undo and redo up to 100 steps" (« Annulez et rétablissez jusqu’à 100 étapes » at `/about/fr` since the merge with main), pinned to the constant by a test.

**D. The editors** (`useEditableHistory.ts`, used by `RichTextEditor` and the new `TableCellEditor`). Until review round 1 the editors also read the input event's type to make a one-character paste, a cut or a deleted selection a step of its own (`isOwnUndoStep`); the engines do not report the editor's own paste that way (F4), so that moved to the document's record (C) and was removed here. A field shows the store's value. Its own typing is committed and not written back (the stored HTML is sanitized and can differ from the DOM, F3). Any other change to the value — an undo or redo, the same block typed in its other copy (the canvas and the Content box), a row inserted, the table formatted from the sidebar — is written in, focused or not, keeping the caret's character offset (H4's trap: a focused editor used to keep stale text). After `runHistory` undoes or redoes a step that changed exactly one text field (`textTargetOf`), that field's editor takes the focus and selects what changed (`changedRange`): the restored text, a caret where text was removed, or, when only the formatting changed, the text it was on. The copy that has the focus keeps it (the Content box); otherwise the canvas copy takes it, and `PosterEditor` selects its block. Table cells no longer use `dangerouslySetInnerHTML`, so typing keeps its order (decision 9).

**E. The page** (`PosterEditor.tsx`, `HistoryButtons.tsx`). `runEditorHistory` shows "Undo"/"Redo" only when a step was applied (decision 7). Undo and Redo buttons sit over the poster area's top-left corner, opposite the save status (the editor has no top bar; at 12 px from the top and 36 px tall the group sits inside fix 03's 64 px gutter around the fitted sheet, INSPECTED, not measured; 52 px further right when the sidebar is hidden, clear of its Show button, TESTED): native buttons, `aria-label` "Undo"/"Redo", disabled with nothing to do, hidden for read-only viewers (the phone share view is one: `mobileShare` is `readOnly && isSmallScreen`, so the condition beside `!readOnly` was redundant and is gone, review R1-F4), titles with the shortcut. A press with the mouse or a finger runs the history as ⌘Z does, the caret going back into the text (decision 4); a press from the keyboard or by assistive technology — a click with a click count (`detail`) of 0, which Enter and Space make — leaves the focus on the button and selects nothing (`runHistory`'s `keepFocus`, review round 2, R2-F2): a focus moved into the text made the next Enter or Space type there, a line break that wiped the redo, or a space over the redone word. Since review round 3 (R3-F1) such a press also selects no block (`runEditorHistory` selects the block only when its editor takes the focus), and any other key pressed on the buttons is theirs: the delete / nudge / duplicate handler and the table's row / column delete and range clear return for a key whose target is inside the buttons' group (`onHistoryButtons`); with a block selected and the focus on a button, an arrow had moved the block and Backspace or Delete removed it, the redo lost. The rest of that handler's guard (a select or another button passes these keys to a selection the user made) is item 22's, parked by the owner. A version restore puts the version in place through the new store action `restoreVersion` as one step: the history before it is kept, the display name is untouched, a version with no usable size takes the poster's current size (as before), and the locked credit mark is kept as on undo (`restoreFromHistory`; the plan had "version restore drops the credit mark" handed on from fix 02).

**F. The toolbar** (`FloatingFormatToolbar.tsx`). A+/A− and the three alignment buttons removed from `FormatToolbarButtons`, so from the floating toolbar and its docked copy above the Content box; every other button kept. Size stays settable in the Edit tab's Font size field, per text level (title, heading, body), and headings' alignment in Style › Headings; body text has no alignment control (it had none that saved).

**Z. Zones that keep their own undo** (`data-own-undo`): the Figure tab (the code box, its preview size, Make's table and variables), Layout › Poster name, the Versions panel (its name), the Authors and References paste boxes, References' Manual Entry, the style preset's name, and the guidelines panel (its checklist and notes) — the drafts that are not the poster until a button uses them. The size fields are not among them: they edit the poster (on commit). The palette designer got `role="dialog" aria-modal="true"` and a name, as a modal should have; that also stops the delete/nudge handler acting behind it. The comments panel is not marked: it is hidden with sharing (section 10).

**Why this shape and not another.** Cancelling only the browser's `beforeinput` (the reproducer's part 2) leaves Firefox's undo with the focus on the page or a dialog button (F1); cancelling only the key leaves the Edit menu and the per-document spill from a field's own undo. A listener on each editor would miss Firefox's history input aimed at a sibling (the confirmer's disagreement 5). Keeping the browser's text undo and syncing the store to it would keep two histories by construction. Re-focusing the field after a cancelled spill was built and then removed: the browsers do not move the focus when the spill is cancelled (F2). Step boundaries come from what the browser says first and the text diff second: the diff alone cannot tell a typed letter from a colour picked, a one-character paste, or where a letter typed in front of a same-letter word went (review round 1); the editors' input event alone cannot tell the editor's own paste (F4). One record on the document gives the same rule to the `<input>` fields (an author's name, a caption) that have no editor component. The browser's own undo in such a field is refused at the store rather than stopped before React (the reviewer's suggestion): the field's React value cannot be read from outside without React's internals, and a value set behind React's back would hand the browser's change to the next keystroke; refused at the store, React puts its controlled field back itself. A composition is decided once, at its `compositionstart`, and not per update (review round 2): each update replaces the text composed so far, so neither the browser's selection nor the text diff can say where a word began; the caret before the composition can. The composition is read only for an edit the browser said was a composition's, so it needs no clearing (each composition begins with its own `compositionstart`); a clear at `compositionend`, at a key pressed outside a composition and at a change of focus were built first and removed, because no user path reaches them (a mutant on each would survive). In scripts written without spaces each composed word is a step: the space rule alone would make a paragraph of Chinese one step. A keyboard press of Undo or Redo is told from a mouse press by its click count (0 for Enter and for Space in Chromium, Firefox and WebKit, B2; assistive technology's activation is expected to click with 0 too, UNVERIFIED), not by a key listener on the button, which an activation with no key event would miss. The keys pressed on the buttons are kept off the poster by a guard in the listeners that act on a selection, not by a key listener on the buttons that stops the event: stopping it would also hide ⌘/ and the other page shortcuts, and the selection's listeners are where the text-field guard already sits (review round 3). Both links of R3-F1 are fixed, not one: leaving the selection alone does not cover a keyboard-only user, whose block is still selected from typing when the focus reaches Undo (B3k), and the guard alone leaves a block the press selected armed for the next control that is not a text field (B3s; F7, MEASURED).

**Tests changed with the behaviour.** `sidebarHistory.test.tsx` (fix 01's) is unchanged from main: its rows change the fields with no `beforeinput`, which since review round 1 is not typing for a sidebar string, so they keep fix 01's time windows (the first version of this fix had changed the Authors › author name row from "J", "Jo", "Joh" to "M", "Ma", "Mar", because "Jane Doe" → "J" read as a deletion by the text alone).
