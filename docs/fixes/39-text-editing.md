# Record 39 — Text editing like PowerPoint: x² and x₂, PowerPoint's superscript and subscript keys, "/" only at the start of a word

## 1. Symptom

A researcher types "H2O" in a text block and wants the 2 low, as in PowerPoint. She selects it: the bar over it has B, I, U, bullets, numbered and Clear, and nothing for superscript or subscript. She presses Ctrl + = as in PowerPoint: nothing happens (on Windows the page would zoom). She types "n/a" and presses Enter: the text becomes "nα" and no new line starts. "w/" becomes "wα", "μg/d" "μgδ", "see Fig. 2/" "see Fig. 2α". In a title, "/al" and Enter puts an α in it.

**The keys, checked in Microsoft's own pages before building** (the brief asked for this; pages read on 2026-10-16 through a page-reading tool, the quotes as it returned them):
- "Use keyboard shortcuts to create PowerPoint presentations" (support.microsoft.com, the article covering PowerPoint for Microsoft 365, for Mac and for the web), **Windows** tab, "Format text": "Apply subscript formatting (automatic spacing)." **Ctrl+Equal sign ( = )**; "Apply superscript formatting (automatic spacing)." **Ctrl+Shift+Plus sign (+)**; "Remove manual character formatting, such as subscript and superscript." Ctrl+Spacebar. **macOS** tab, "Format text": subscript **⌘+Control+Equal sign (=)**; superscript **⌘+Control+Shift+Equal sign (=)**; removing it Control+Spacebar. Its zoom rows: "Zoom in." ⌘+Plus sign (+) on macOS and Ctrl+Plus sign (+) on Windows (PowerPoint's own zoom, not the browser's). The Web tab lists no superscript or subscript key.
- "Format text as superscript or subscript" (support.microsoft.com, PowerPoint), **Windows**: "For superscript, press Ctrl, Shift, and the Plus sign (+) at the same time." and "For subscript, press Ctrl and the Equal sign (=) at the same time." **macOS**: "For superscript, press Control, Shift, and the Plus sign (+) at the same time." and "For subscript, press Control and the Equal sign (=) at the same time. (Do not press Shift.)"

So on Windows the keys are **Ctrl + Shift + =** (the Plus sign is Shift + = on a US keyboard) and **Ctrl + =**, which the design doc expected. **On a Mac Microsoft's two pages agree on Control, not ⌘**, and differ only on whether ⌘ is held with it; the design doc's guess (⌘ + Shift + = and ⌘ + =) is not Microsoft's, and ⌘ + = is every Mac browser's zoom-in. Postr takes **Control + Shift + = and Control + = on a Mac, with or without ⌘** (both of Microsoft's forms), and leaves ⌘ + = to the browser. On Windows the Windows key with Ctrl is not taken. Ctrl / Control + Space (clear character formatting) is not built: the bar's Clear does it (section 10).

## 6. Root cause

- **T1, T2 (H1).** Nothing made sub- or superscript: the bar had no button for them (`FloatingFormatToolbar.tsx:248-310`, main) and the editor's `handleKeyDown` read only the slash menu's Esc, Tab and Enter and the single-line Enter (`RichTextEditor.tsx:239-257`, main). The sanitizer and the cleaner always kept `<sub>` and `<sup>` (`sanitizeHtml.ts:63-64`, `pasteClean.ts:5`), so a paste was the one way to get them, and T3 held (H7 refuted).
- **Why not the engines' own commands (H2).** They decide on and off from the computed `vertical-align`, and Tailwind's preflight draws `sub, sup` with `vertical-align: baseline` and a relative offset (preflight.css:133-139; the print document restates the rule, `printSheetBase.ts:48-50`, record 30). In Chromium and WebKit superscript text therefore reads as not superscript: a second x² would apply it again. Overriding the rule would change how every sub and sup draws (the author markers too) against the print document and the PowerPoint file, which record 30 matched to the editor. So the state is read from the markup and the change made there (`poster/scriptFormat.ts`).
- **T4 (H3, H4).** The matcher took a `/` anywhere (`slashCommand.ts:40`, main: `/\/([a-zA-Z0-9]*)$/`), and Enter and Tab both inserted `filterSymbols(prefix, 1)[0]` (`RichTextEditor.tsx:245-251`, main): typing "n/a" and Enter is a slash in a word and a new line, read as "insert the first symbol starting with a". There was no highlight to move (`aria-selected={false}` on every option) and the list stopped at 8.
- **The bar's state (H5).** It was read only on `selectionchange` (`RichTextEditor.tsx:324-357`, main), which Firefox does not fire when `execCommand('bold')` leaves the selection where it was; bullets and numbered were drawn with a constant `false` (`FloatingFormatToolbar.tsx:264-265`, main).
- **The line join (H6).** `insertSymbolViaExec` selects the `/prefix` by character offsets and turns each into a DOM point with `rangeFromPlainOffset`, whose test `consumed + len >= offset` puts a point at a boundary between two text nodes into the earlier node. A `/` typed at the start of a line made with Enter is the first character of a text node in that line's `<div>` (or after a `<br>`), so the range began at the end of the line before and `insertText` replaced the line break with the symbol. Older than this fix; it showed only because T4 makes the menu at a line start a rule. **The first version of this record said the side fix covered a line after a `<br>` too; in Firefox it did not** (the review, H6b): there the range started in the right text node, and Firefox's own `insertText` over that whole node deleted the `<br>` before it.
- **Found by the review (section 9), each measured here before correction 1:**
  - *A copy of the scripted characters alone (R1-F1, H7).* Chromium and WebKit serialise a selection inside one `<sup>` or `<sub>` as a `<span>` with the computed style, and that style has no raise (the preflight rule again: `vertical-align: baseline`), so the paste stores a plain "2"; a selection that reaches outside the `<sup>` makes them write the element itself, and they write `<b>` around a selection inside bold (TE3ik clean before: "OL" copied from "BOLD" stored `<b>OL</b>` in all three), so it is the sub and sup only. The same root cause as H2: the engines read sub and sup through a computed style the page's base rule sets to baseline.
  - *Firefox's insertText (R1-F2, H6b)*, above.
  - *The numeric keypad (R1-F3).* `isEqualKey` accepted the character "+" from any key, so Control + the keypad's + (key "+", code `NumpadAdd`) was subscript and with Shift superscript, cancelling Windows browsers' Ctrl + keypad + zoom (TE2n observed in the three engines).

## 7. The change

- **`poster/scriptFormat.ts` (new).** `scriptKeyAction(e, mac)`: Control (Ctrl) with the = key, Shift → superscript, without → subscript; the = key by its character ("=" or "+") or its physical key (`Equal`); Alt never; ⌘ with Control only on a Mac (Microsoft's Mac table), so on Windows the Windows key with Ctrl is left alone; ⌘ + = alone is not it. `scriptTitle(tag, mac)`: "Superscript (⌃⇧=)" / "Subscript (⌃=)" on a Mac, "Superscript (Ctrl+Shift+=)" / "Subscript (Ctrl+=)" elsewhere. `scriptState` and `listState` read the selection from the markup (every covered character inside a `<sup>`/`<sub>`, a `<ul>`/`<ol>`; a caret: inside one). `toggleScriptIn(host, range, tag)`: on, unless the selected text is all `tag`, then off; the selection's text nodes are cut at its ends, each lifted out of any sub or sup above it (the ancestor split around it; a part kept when it holds text or a line break), then wrapped in `tag` when turning on; empty sub / sup unwrapped, neighbours of one kind joined, the text normalised and the same characters selected again (so the button can be pressed again). `toggleScript(tag)` does that on the window's selection in its editing host and fires the host's `input` event with the type a browser gives its own command (`formatSuperscript` / `formatSubscript`); the editor commits it like any input, and a change of markup with the same text is an undo step of its own (`stores/historySteps.ts`, fix 12). ## 10. Limits and follow-ups

- **x² and x₂ for the next letters typed** (PowerPoint's keys with only a caret): not built; with only a caret the keys are taken in text and do nothing (TESTED), and the bar shows only over a selection. Typing right after a subscript at a block's end continues it (MEASURED in the three engines, `TE-I-type-after-sub`), as word processors do; the way out is to select it and press x₂. A caret toggle would need its own design: the engines' typing style reads the computed `vertical-align`, the same trap as H2 (INSPECTED). PLAN's Later list.
- **A real Windows browser's own zoom**: in Playwright's three engines the page receives Ctrl + Shift + = and Ctrl + = and cancels them in text (MEASURED); whether Chrome, Edge or Firefox on Windows zoom before the page can cancel is UNVERIFIED (Playwright's keys reach the page only, `TE-I-zoom`). Outside text the keys stay the browser's (MEASURED, TE2o). Manual flow §41. Later list.
- **Keyboard layouts where = needs Shift** (German Shift + 0): the editor reads the "=" and "+" characters or the physical = key (never the numeric keypad's), so on a German layout Ctrl + the "+" key (no Shift) is subscript, Ctrl + Shift + 0 superscript and Ctrl + the ´ key on the US = key's place subscript, and on a French one Ctrl + = subscript (MEASURED with dispatched keydowns in the three engines, `TE-I-layouts`; a real keyboard UNVERIFIED). This record's first version said subscript had no key there (INSPECTED, and wrong: the review's R1-F4). Ctrl + "+" is German Windows browsers' zoom-in, cancelled in text, the trade T2 makes for Ctrl + = on a US keyboard. PowerPoint's own behaviour on those layouts UNVERIFIED. Later list.
- **"/" right after an opening bracket, a quote, an emoji or CJK text opens no menu** (the review's R1-F7; MEASURED by the reviewer, the matcher INSPECTED here): T4 names a space, a line start and the block's start, so "(α)" needs a space typed and deleted, and CJK text, written without spaces, the same; main opened the menu on "/" anywhere. Whether an opening bracket or quote is a word start is an owner question for later (`(?:^|[\s(\[{"'“‘«])` would keep every in-word example of the design doc closed). Later list.
- **"/al", ←, Tab gives "αl"**: the menu reads the prefix up to the caret, so a symbol inserted with the caret inside "/al" keeps the letters after it (the reviewer's R12 in the three engines; main the same, INSPECTED). Not changed. Later list.
- **The editor's own copy** (correction 1) is taken only for a selection wholly inside one `<sup>` or `<sub>`; it writes the bare tags and the text, so such a copy pasted into another application has that application's font and colour, not the poster's (INSPECTED; every other copy is still the browser's, with its computed style). It calls `preventDefault` and does not stop the event: a document-level copy handler of another fix (record 35, block copy and paste, in another tree) still sees it, with `defaultPrevented` set (INSPECTED; a merge note).
- **The keys in table cells, captions and sidebar fields** stay the browser's (no format bar there either; INSPECTED). Later list.
- **The bar's buttons act on a mouse press** (`onMouseDown`, as B, I and U always did); a keyboard user has the keys (INSPECTED). Later list.
- **⌘/Ctrl + Space** (PowerPoint's clear character formatting): not built; the bar's Clear (`removeFormat`) does it. Later list.
- **The PowerPoint file's subscript baseline is −40000** (pptxgenjs's value, MEASURED, TE3x); PowerPoint's own subscript offset is UNVERIFIED (the manual flow opens the file). Later list.
- **The docs' "66 symbols"** was a miscount: `symbols.ts` holds 65 (MEASURED, counted in `keepWorkTextEdit.mjs` `SYMBOL_COUNT` and in `textEditing.test.tsx`); corrected in the inventory (2.3), bounded-designs §3.2 and the feature graph. No symbol added (out of scope).

Every WebKit reading matched Chromium's (and, for TE3i before correction 1, the reviewer's R22), and each clipboard read held this page's own text.
