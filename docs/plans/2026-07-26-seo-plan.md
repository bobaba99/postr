# Postr SEO — Implementation Plan

**Goal:** Make postr.sh discoverable by researchers who are about to build a conference poster, on all three surfaces that matter — Google organic, AI assistants, and links pasted into lab Slacks — starting from a site that today emits one identical bare HTML shell for every URL.

**Architecture:** No framework migration. Keep `react-router-dom` declarative routing and the Vite SPA build. Add three layers: (1) a shared route-metadata module consumed by both a ~60-line client hook and a post-build injection script, so crawler-visible head tags and browser-tab titles can never drift; (2) a `node scripts/prerender.mjs` step that writes `dist/<route>/index.html` per static public route — Vercel's filesystem lookup wins over the existing catch-all rewrite, empirically confirmed against this deployment; (3) two Vercel Edge Functions that inject per-entry head tags for `/gallery/:entryId` and `/s/:slug`, which are unbounded and change without a deploy. Programmatic pages are generated from data that already lives in this repo — `GUIDELINES` in `GuidelinesPanel.tsx`, `POSTER_SIZES` + `POINTS_PER_UNIT` in `constants.ts`, `PALETTES`, and `gallery_entries`.

**Tech stack:** Existing Vite 8 / React 18 / react-router-dom 6 / Tailwind, plus `@vercel/og` for social cards. No new runtime dependencies in the React app.

---

## 1. Where we stand

`apps/web/index.html` is eleven lines: charset, viewport, favicon, `<title>Postr</title>`. There is no meta description, no canonical, no Open Graph, no Twitter card, no JSON-LD, no robots meta. There is no `robots.txt` and no `sitemap.xml` — `apps/web/public/` contains a favicon, a `version.json`, a seed poster, and two stray 16KB/63KB logo HTML files that are live crawlable URLs at `postr.sh/logo-preview.html` right now. Worse than absent: because of the catch-all rewrite, both `/robots.txt` and `/sitemap.xml` currently return **HTTP 200 with `content-type: text/html`** and the SPA shell as the body (verified live 2026-07-27), rather than a clean 404. A 404 robots.txt means "crawl everything" and is harmless; a 200 serving HTML is a malformed robots.txt that Google must parse and discard line by line, and a `sitemap.xml` that returns HTML will hard-fail on submission to Search Console. This is why Phase 1's filesystem-precedence property is load-bearing and not merely tidy — the files must actually win over the rewrite, and Phase 0 must verify `content-type: text/plain` on `/robots.txt`, not just that the file was committed. Grep for `document.title`, `Helmet`, or `og:` across the app returns nothing: every one of the eight public routes serves the identical title. `apps/web/vercel.json` rewrites `/(.*)` → `/index.html` with no status override, so every nonexistent path — `/gallery/<garbage-uuid>`, `/asdf`, every retracted gallery entry — returns HTTP 200 with the SPA shell, which is an unbounded soft-404 space. In practice: Googlebot *does* render JavaScript (Google deleted its own JS caution from the docs in March 2026), so Postr is technically indexable on Google — but as eight byte-identical documents, which is a canonicalization and soft-404 problem before it is a ranking problem. Every non-Google consumer gets nothing. `facebookexternalhit`, `Twitterbot`, `LinkedInBot` and `Slackbot` have never executed JavaScript, so every link a researcher pastes into a lab Slack or onto Bluesky today renders as a bare URL with no title, no description, and no image — for a product whose entire artifact is a beautiful visual, that is the single most expensive defect on the site. AI crawlers (GPTBot, ClaudeBot, PerplexityBot, OAI-SearchBot) fetch raw HTML only and see `<div id="root"></div>`, so Postr cannot currently be cited by any assistant. And `/s/:slug` share links — users' unpublished, in-progress research — have no `noindex` anywhere, which is a privacy exposure, not just an SEO one.

## 2. The core decision: rendering

### Recommended — build-time HTML injection + Edge shell functions

Two mechanisms, neither of which touches `apps/web/src/routes.tsx`:

**A. Static public routes** (`/`, `/about`, `/gallery`, `/privacy`, `/cookies`, `/terms`). A post-build Node script reads the built `dist/index.html`, rewrites the `<head>` per route from a shared metadata module, and writes `dist/about/index.html`, `dist/gallery/index.html`, etc. It also injects the same marketing prose the React components render, from a shared `staticCopy.ts`, so crawlers get real text instead of an empty div. React hydrates over it normally.

**B. Dynamic routes** (`/gallery/:entryId`, `/s/:slug`). A Vercel Edge Function fetches the row with the anon key against the existing `gallery_entries_public_select` RLS policy, injects head tags into the shell, and returns it — identically — to every requester. No user-agent sniffing, no cloaking. Always fresh, so retractions take effect immediately and no rebuild-on-publish trigger is needed.

**Effort: 4 dev-days.** **Risk: low.** Nothing in the React tree changes. If the prerender script breaks, `dist/index.html` still exists and the catch-all still serves it — the failure mode is "back to today," not "site down."

### Runner-up — React Router v7 framework mode with `ssr: false` + `prerender`

This works. It was empirically verified: `@react-router/dev@7.18.1` installs cleanly on React 18.3.1 + Vite 8.0.8, `npx react-router build` succeeds, and the prerendered HTML contains real per-route `<title>` and `<meta>`. `ssr: false` + `prerender` even auto-removes the server build, so the Vercel static deploy survives.

**Effort: 5–8 dev-days.** **Risk: medium.** The cost is not the prerender config — it is that `prerender` is available **only in Framework Mode**, so reaching it requires *two* migrations stacked: `react-router-dom@6` → `react-router@7` (removing `react-router-dom` entirely, or npm silently installs both and you get two React Router contexts that break at runtime, not at install), *and* declarative → framework mode (new `react-router.config.ts`, a `routes.ts` route-config module, `root.tsx`, `entry.client.tsx`; `index.html` and `src/main.tsx` both disappear). The official catchall-route pattern (`route("*?", "catchall.tsx")`) keeps the editor untouched, which genuinely de-risks it — but it is still a routing rearchitecture on a 140-file app with GSAP timelines, canvas refs, and `pdfjs-dist`.

### The decisive reason

**Googlebot renders JavaScript.** That is confirmed against Google's own primary docs and against Vercel/MERJ telemetry (100% render success on 37,000 matched page pairs; median crawl-to-render 10s). Google's AI Overviews and AI Mode are served from the same Googlebot index — per Google Search Central, "there are no additional technical requirements" beyond normal indexability. So prerendering buys **nothing on the entire Google surface**. What it buys is (a) social unfurl cards, which is definitional and not in dispute, and (b) AI assistant citations, which rests on a single Vercel study from December 2024 that nobody has independently replicated.

Given that the audience for prerendered HTML is "crawlers that read raw HTML and never execute a script," those crawlers need exactly two things: the head tags and the primary text. They do not need a hydrated React tree. Which means the expensive way (framework mode) and the cheap way (string injection) produce the *same observable result for the consumer that needs it*, and one of them costs a routing rearchitecture.

**Take the injection script. Revisit framework mode only if Postr later needs genuine per-request SSR** — e.g. personalized gallery pages or a server-rendered editor preview. That is not on the roadmap.

### One thing that is NOT an SEO decision but must be said

`react-router-dom@6.30.3` is installed. React Router v6 reached **End of Life on 2026-06-17** with the v8 GA and will receive no further security updates. `npm audit` reports four open advisories against it right now; **three have no v6 patch and never will**, including CVE-2026-53668, which affects even the terminal 6.30.4 release. Two of them (CVE-2026-53669 open redirect via backslash in `<Link>`/`useNavigate`; GHSA-2j2x-hqr9-3h42 protocol-relative open redirect) hit declarative-mode client APIs Postr uses throughout. All four are Moderate; the practical exposure is phishing-shaped, not data-breach.

The fix is `react-router@7.18.1`, **staying in declarative mode** — v7's peer dep is `react: ">=18"`, so no React upgrade is needed. Ship it as its own commit, on its own justification, ahead of or alongside this plan. **Book zero SEO value against it.** Do not target v8: it requires `react >= 19.2.7` and `node >= 22.22.0`, and CI currently pins Node 20 (`.github/workflows/ci.yml:41,65`). And do not let `npm audit fix --force` run unattended in CI — npm reports `fixAvailable: true`, but the "fix" is a breaking major bump.

## 3. Phased plan

Ordered by impact ÷ effort. Phases 0–1 are the technical baseline; nothing after them works without them.

### Phase 0 — Baseline metadata & crawl control · **2 dev-days** · no dependencies

The cheapest, highest-leverage work in the whole plan. No architecture change, no build-pipeline change, ships Monday.

| `apps/web/public/robots.txt` | **new** — full content in §6. |

| `apps/web/src/routes.tsx:74` | Gate `/debug` behind `import.meta.env.DEV`. It is publicly routable with no guard today. |

**Also in this phase (non-code, ~1h):** verify Google Search Console via **DNS TXT** on `postr.sh` — HTML-file and meta-tag verification both fail against the catch-all rewrite. Create the Domain property plus URL-prefix properties for both hosts, then one-click import to Bing Webmaster Tools. This is time-critical for two independent reasons: Search Console's generative-AI performance report has **no backfill**, so every week unverified is baseline data permanently lost; and the entire measurement-driven half of this plan (§8's striking-distance workflow) is gated behind having first-party query data at all, which takes 4–8 weeks to accumulate after indexation.

**Also (5 min, Vercel dashboard):** change the apex → www redirect from its current **307 (temporary)** to permanent. Verify with `curl -sI https://postr.sh/ | head -1`. Every `rel=canonical` in §6 points at the `www` host, so this is a prerequisite for the canonical strategy, not a nicety.

**Why `X-Robots-Tag` and not `Disallow: /s/`** — a robots.txt `Disallow` stops the *crawl*, which means the crawler never fetches the page and never sees the `noindex`, so a URL discovered from an external link can still be indexed as a bare listing. Worse, Slackbot/Twitterbot/LinkedInBot honour robots.txt, so disallowing `/s/` kills the share previews that are the core viral loop. **Allow the crawl, forbid the index.** Google's Dec 2025 guidance also notes JS-injected `noindex` is unreliable, which is a second reason the header is primary and the meta tag is belt-and-braces.

**Measurable outcome:** `curl -s https://www.postr.sh/about | grep -c 'name="description"'` returns `0` (client-only — expected, this is what Phase 1 fixes), but Search Console URL Inspection on `/about` shows a distinct rendered title and description. All eight public routes report distinct titles. `curl -sI https://www.postr.sh/s/<slug> | grep X-Robots-Tag` returns `noindex, nofollow`. Zero soft-404s attributable to `/logo-preview.html`.

Two of these must be asserted on **content-type, not just status**, because the catch-all makes every path return 200:

```bash
curl -sI https://www.postr.sh/robots.txt | grep -q 'content-type: text/plain' || echo "FAIL robots.txt still served by the SPA rewrite"
curl -sI https://postr.sh/ | head -1 | grep -q '308' || echo "FAIL apex still 307 (temporary)"
```

### Phase 1 — Crawler-visible HTML · **4 dev-days** · depends on Phase 0

**Deliverables**

| File | Change |
|---|---|
| `apps/web/scripts/prerender.mjs` | **new** — reads `dist/index.html`, writes `dist/<route>/index.html` per entry in `STATIC_ROUTE_META` (skipping `noindex` routes). |
| `apps/web/scripts/gen-sitemap.mjs` | **new** — writes `dist/sitemap-static.xml` from `STATIC_ROUTE_META` + `FIELD_OPTIONS`. |
| `apps/web/src/seo/staticCopy.ts` | **new** — headline/subhead/feature strings imported by both `Landing.tsx` and the prerender script. This shared import is the *only* thing preventing crawler-visible copy from drifting away from rendered copy, which is what would turn honest prerendering into accidental cloaking. |
| `apps/web/package.json` | `"build": "tsc -b && vite build && node scripts/prerender.mjs && node scripts/gen-sitemap.mjs"` |
| `apps/web/api/shell/gallery.ts` | **new** — Edge Function, injects head tags for `/gallery/:id`, returns real 404 for missing/retracted rows. |
| `apps/web/api/shell/share.ts` | **new** — same for `/s/:slug`, with `noindex` + rich OG from `posters.thumbnail_path`. |
| `apps/web/api/sitemap-gallery.ts` | **new** — Edge Function, `s-maxage=3600`, reads `gallery_entries` where `retracted_at is null`. |
| `apps/web/api/og/gallery.tsx` | **new** — `@vercel/og` composed 1200×630 card. |
| `apps/web/vercel.json` | Insert function rewrites **before** the catch-all (rewrites evaluate in array order). |

```json
"rewrites": [
  { "source": "/sitemap-gallery.xml", "destination": "/api/sitemap-gallery" },
  { "source": "/gallery/:id",         "destination": "/api/shell/gallery" },
  { "source": "/s/:slug",             "destination": "/api/shell/share" },
  { "source": "/(.*)",                "destination": "/index.html" }
]
```

**Two landmines, both silent.**

1. **Emit directories, never flat files.** `cleanUrls` defaults to `false` and is unset here — verified live: `/logo-final.html` returns the 16KB file, `/logo-final` returns the 932-byte SPA shell. So `dist/about.html` would fail with a green build, a 200 status, and zero crawler-visible change. Write `dist/about/index.html`. Prefer this over setting `cleanUrls: true`, which would force `/index.html` to 308-redirect to `/` and put the app's only routing rule at risk to solve a problem the directory shape solves for free.

2. **Assert on byte size in CI.** Every route returns 200 whether prerendering worked or not. The SPA shell is a fixed **932 bytes**, so `size_download == 932` is a reliable silent-failure detector:

```bash
# apps/web/scripts/verify-prerender.sh — run against the Vercel preview URL
for r in "" about gallery privacy cookies terms; do
  n=$(curl -s -o /dev/null -w '%{size_download}' "$PREVIEW/$r")
  [ "$n" -gt 2000 ] || { echo "FAIL /$r served the ${n}B shell"; exit 1; }
done
curl -s "$PREVIEW/about" | grep -q 'name="description"' || { echo "FAIL no meta"; exit 1; }
```

**Flat files need no verification** — `/version.json`, `/favicon.svg`, and `/seeds/welcome-cat-poster.postr` already win over the catch-all in production today. Filesystem-before-rewrites is guaranteed here *only* because `vercel.json` uses the modern `rewrites` property; the legacy `routes` property would bypass the filesystem without an explicit `{"handle":"filesystem"}` phase. Do not convert.

**Measurable outcome:** `curl -A GPTBot https://www.postr.sh/gallery` returns entry titles in the response body. Pasting a `/gallery/:id` URL into Slack renders a card with the poster image. `curl -s https://www.postr.sh/gallery/<retracted-id> -o /dev/null -w '%{http_code}'` returns 404.

### Phase 2 — Conference requirement pages · **5 dev-days** · depends on Phase 1

`GuidelinesPanel.tsx` already holds a structured `GUIDELINES` array (line 31) with 7 conferences — APA, SfN, APS, ACNP, SOBP, ECNP, SPSP — each carrying `conference`, `field`, `size`, `sizeNote`, `fonts: FontSpec[]`, `tips[]`, and a citation `url` + `urlLabel`. The data model already exists; the work is (a) lifting it out of the panel into a shared module, (b) re-verifying every row against the primary source, (c) adding `orientation`, `unitSystem`, `verifiedOn`, and `meetingYear`.

**Fix these data errors before anything ships.** The SfN row is internally contradictory — `size` says `72" × 48" (6' × 4')` but `sizeNote` says `Board is 8'×4'`. Verified against `sfn.org/meetings/neuroscience-2026/call-for-abstracts/presentation-formats/poster-sessions` on 2026-07-27: SfN assigns **a 6 ft (1.8 m) wide × 4 ft (1.2 m) high board — 72 × 48 in, landscape**, unchanged since at least 2014, and it is a **maximum**, not a required poster size. Copy must say "poster board: 6 ft × 4 ft, landscape — maximum size." The ECNP row cites a `congress2025` URL and gives 95 cm × 140 cm portrait; independent checking surfaced A0 portrait (841 × 1189 mm) — one of these is stale, and a wrong dimension gets someone's poster rejected. That failure mode destroys trust with the exact audience Postr needs.

**Do not build a scraper as a blocking dependency.** Ship a static, human-reviewed table where every row carries `sourceUrl` + `verifiedOn` + `meetingYear`, surfaced as "Verified 27 Jul 2026 — check official guidance" with the link, mirrored into JSON-LD `dateModified`. One manual re-check per meeting cycle is proportionate. If a verifier is ever built, encode two gotchas or it will produce false negatives: SfN's dimensions live on the *child* `/poster-sessions` URL (the parent `/presentation-formats` has none), and `/presenter-resources/poster-presentations` serves a **soft-404 at HTTP 200** with full nav chrome for the current meeting year until SfN publishes it — check for the 404 title string, not the status code.

**URL pattern:** `/poster-requirements/:conference` (deliberately *not* under `/gallery/`, so Postr's editorial content is never structurally confused with UGC). Index page at `/poster-requirements`.

**Deliverables:** `apps/web/src/seo/conferences.ts` (lifted from `GuidelinesPanel.tsx`, imported back by it), `apps/web/src/pages/ConferenceRequirements.tsx`, `apps/web/src/pages/ConferenceIndex.tsx`, routes + prerender entries.

**Measurable outcome:** 7 pages indexed, each with a working "start a poster at this size" deep link. First long-tail impressions in Search Console for `[conference] poster template` / `[conference] poster size` within 8 weeks.

### Phase 3 — Poster size pages · **3 dev-days** · depends on Phase 2

`POSTER_SIZES` (`constants.ts:74`) holds 8 presets. `POINTS_PER_UNIT = 7.2` and the `ptToUnits`/`unitsToPt` helpers mean each page can compute genuinely different values: exact pixel dimensions at 150/300 DPI, mm/cm/in conversions, the printed point size of the default title/heading/body at that canvas, roughly how many words fit at the 24pt body minimum, which of the five `templates.ts` layouts (3-Column Classic, 2-Col Wide Figure, Billboard, Sidebar + Focus, Blank) actually work at that aspect ratio, and which conferences from Phase 2 specify it.

**Hard rule — the merge test.** Every page must contain at least one value *computed for that size* that differs from its neighbours. If two size pages would render identical computed tables, they are one page with two URLs: pick a canonical and 301 the other. Cross-link portrait↔landscape pairs explicitly (`36×48` ↔ `48×36`) to pre-empt duplicate-detection.

**Do not add** A0-in-pixels conversion pages. That SERP is owned by pure-play paper-size permutation farms (a0-size.com, papersizes.online, pixexact) with years of accrued authority on exactly that, and the answer is a one-line AI Overview. The academic framing (`standard conference poster size`, `48x36 poster template`, `A0 vs 48x36`) is where the SERP is held only by small commercial sites, not calculator farms.

**URL pattern:** `/poster-size/:size` → `/poster-size/48x36`, `/poster-size/a0-portrait`. Realistic ceiling ~18 pages (the 8 presets plus A1, A2, 24×48, 30×40, 36×60, 44×44, 72×48). Stop there — the tail (`37×29`) is where this turns into spam.

**Measurable outcome:** ≥12 of 18 indexed within 6 weeks (not all — partial indexation is the realistic outcome on a young domain). Non-zero impressions on `standard conference poster size`.

### Phase 4 — Figure-readability tool page + .edu outreach · **4 dev-days + ongoing** · depends on Phase 1

`apps/web/src/poster/readability.ts` is **360 lines of dependency-free client TypeScript** with tests at `apps/web/src/poster/__tests__/readability.test.ts`. It parses `ggsave()`, `figsize`, `theme_*(base_size)`, `rcParams`, `sns.set_context`, computes effective print pt after block scaling, scores against thresholds (axis titles 18pt, tick labels 14pt, captions 12pt), back-calculates the smallest passing `base_size`, and emits a copy-paste snippet. It ships as a standalone static page today with essentially no new logic.

**This is deliberately not justified as a traffic asset.** Generative UI — Google's AI Mode Canvas (all US users March 2026, free in Search this summer) and OpenAI's Apps SDK — now generates interactive calculators inline on demand, and a researcher pasting ggplot2 code into a chatbot gets a competent answer without ever visiting postr.sh. Tool pages whose value is a *computed answer* are commodity now.

It is justified on **link acquisition and conversion**, which survives that:

- The R/Python figure-sizing SERPs are the weakest competitive field found anywhere in this research — `ggplot2 font size for poster axis labels` returns datavizpyr, fontorbit, codestudy.net, w3tutorials; `matplotlib figure size for conference poster dpi` returns pythonforthelab, fedmsg, educative. Not one is a poster tool. Not one has poster authority.
- The closest existing product, `sci-draw.com/figure-checker`, takes **image uploads only** (not code), is framed around *journal* column widths (not poster print size), and requires sign-in at 10 credits per figure. Postr's differs on input, framing, and price simultaneously.
- **Librarians link free standalone utilities, never product pages.** University of Minnesota's poster guide (`libguides.umn.edu/posters`) links `canva.com/colors/color-palette-generator/` — a VC-funded competitor's domain — but only at a free utility URL, never at `canva.com/posters/templates/research/`. `learnui.design`'s accessible-colour generator got in on the same basis. That is the entire pattern.

**URL:** `/tools/figure-readability` — a bare utility URL, fully functional with no account, editor upsell below the fold.

**The outreach motion** (~1–2 days/week, indefinite, non-engineering): prospect via `site:libguides.com "research poster"`, `inurl:libguides poster (PowerPoint OR Canva OR InDesign)`, `site:guides.lib.*.edu poster`, plus Springshare's community index. Qualify on: guide already lists multiple tools, Last Updated within ~18 months, real .edu. LibGuides render the owner's name and email in a profile box on the page, so the contact is already published. Email from a named human, five sentences, subject naming their exact guide, lead with the readability checker (it is the problem they personally field), close with *"would this be useful to your students?"* — never *"would you link to us?"*. One follow-up at ten days, then stop.

**Timing is the biggest free multiplier:** librarians refresh guides in **late August and early January**; US undergraduate symposia cluster March–April with posters built 2–6 weeks prior. Sending in May throws the list away. Run ~30 qualified guides/week in those two windows.

**Measurable outcome:** 5–15 `.edu` referring domains by month 6, visible in Search Console → Links. Referral sessions from `libguides.*` domains.

### Phase 5 — Gallery: text extraction, indexation gate, discipline hubs · **8 dev-days** · depends on Phase 1

Read `apps/web/src/pages/GalleryEntry.tsx`: the rendered page is a field badge, optional conference/year, an H1, one `<img>`, an optional PDF link, optional notes, and a takedown notice repeated identically on every entry. Strip the boilerplate and a typical entry has **under 30 words of unique crawlable text**. `conference`, `year`, and `notes` are all nullable (`gallery.ts:60-64`), so an entry page can legitimately render as title-plus-discipline-label.

The gallery *is* Postr's only asset with a structural moat — a proprietary corpus of real published academic posters that generative UI cannot manufacture and must cite. The one commercial page that outranks the `.edu` wall for `research poster examples` is `animateyour.science`, and it wins with **four real, named posters critiqued across six fixed dimensions** — published June 2021, last updated May 2022, still winning. Four posters and four years stale is the bar. But that page wins on *annotation*, not on page count: generating 500 templated stubs from `{title, field, image}` backfires.

**The highest-leverage single fix is text extraction.** OCR / PDF text extraction at publish time, rendering the poster's own title, authors, abstract and section text as real text on the page. It is the poster's content, published deliberately through a consent flow; it makes the page substantive rather than an image with a caption, accessible to screen readers, and findable by researchers searching the actual subject matter.

**Indexation predicate — machine-checkable, ALL must hold, else `X-Robots-Tag: noindex`:**

| # | Condition | Why |
|---|---|---|
| i | entry age ≥ 7 days | spam-decay window; survives retraction lag |
| ii | author is not anonymous | mirrors Google's documented advice to noindex content from users with no platform reputation |
| iii | extracted poster text ≥ ~150 words | a real content layer exists |
| iv | `notes` ≥ 120 chars **or** an extracted abstract exists | human context, not just metadata |
| v | title is not a placeholder | `Untitled Poster`, `Poster`, empty-ish |
| vi | `retracted_at is null` | — |

Evaluate nightly, flip the flag, generate `sitemap-gallery.xml` **from the predicate** so the sitemap is a curated positive-signal set rather than a dump. Publishing stays frictionless; only *indexation* is gated. Retracted → **HTTP 410**, dropped from the sitemap same-day.

**Discipline hubs** `/gallery/discipline/:field` — 11 possible from the `field` enum. **Gate at ≥8 index-eligible entries from ≥5 distinct authors**, plus a human-written discipline-specific editorial intro. Eleven near-empty listing pages that differ only by a heading is the single clearest scaled-content pattern in this plan. `humanities` and `other` will likely never clear and should not get pages.

**Pagination is a blocker here.** `apps/web/src/pages/Gallery.tsx:32` calls `listGallery({ field })` with no `offset`, and `listGallery` defaults to `limit: 24` (`gallery.ts`). Entry #25 onward has **zero internal links pointing at it, forever**. Add `/gallery/page/:n` with real `<a href>` links — not `onClick` handlers, which a non-JS crawler cannot follow. Self-canonical each page; never canonical page 2+ back to page 1.

**Also:** gallery URLs are raw UUIDs today. Move to `/gallery/{slugify(title)}-{id.slice(0,8)}`, 301 from the bare UUID, **before** the sitemap goes live. And images are served from `*.supabase.co` via `publicUrlFor()` — proxy them through postr.sh so image-search associations and OG image trust accrue to the right domain.

## 5. Programmatic page families

**The governing safety test.** Google's scaled-content-abuse policy targets "generating many pages without adding value"; volume itself is explicitly not the violation. Three conjunctive tests, applied to every family before it ships:

1. **Substitution test.** Can page N+1 be produced from page N by replacing variables, with no new human research, no new asset, and no new computation? Every family must **fail** this.
2. **Deletion test.** If this page vanished, would a specific human be worse off, and can you name the question they arrived with? "Someone searching [keyword]" is not an answer.
3. **One-step test.** Does the page answer something the visitor could not get from the primary source in one step? If a reader could just click through to SfN's own PDF and be equally served, don't publish.

Word count is the wrong bar. A 200-word conference page saying *"SfN boards are 6 ft × 4 ft but that's a maximum — the six inches of margin are intentional, don't fill them"* passes all three. A 1,200-word discipline page that only swaps a palette hex fails all three.

That is an unbounded crawl surface and an abuse vector. Year facets are worse: nobody asks "posters from 2019." Keep both as client-side filter state with `noindex` on any URL carrying them, and if conference browsing later proves valuable, surface the entries as a *section on* `/poster-requirements/sfn` rather than minting a parallel family.

**Internal linking shape.** The tell that flags a page set as generated is an identical link block on every page. Avoid a global footer listing all 18 size pages and all 40 conference pages. Prefer contextual, asymmetric links: a conference page links to the 1–2 sizes it actually specifies; a size page links to the specific conferences that use it. The outbound set genuinely differs page to page.

## 6. Metadata & structured data spec

Canonical origin is `https://www.postr.sh`. Uniform rule: origin + lowercase pathname, **no trailing slash except root**, all query params stripped. `/path/` 308s to `/path` via `"trailingSlash": false`.

**Correction — the apex redirect is a 307, not a 308.** Measured live 2026-07-27: `curl -sI https://postr.sh/` returns `HTTP/2 307` with `location: https://www.postr.sh/`, and `https://postr.sh/gallery` likewise 307s. 307 is a *temporary* redirect. **Standing copy constraint — no AI framing, anywhere.** Every title, description, heading, and body string produced by this plan is marketing copy and is bound by the project rule that Postr collateral must never mention AI, and that features are named by the **workflow** the reader performs, not the capability behind it ("Enter institutions once. Group semantics: consecutive `User-agent:` lines followed by one rule block form a single group — spec-correct. Note also that user-initiated fetchers (ChatGPT-User, Claude-User) may not honour robots.txt by their vendors' own documentation — that is fine, since a user pasting their own share link is their choice.

**Why allow the training crawlers.** The fashionable hedge is "block training, allow search." That exists to protect monetizable proprietary content; Postr has none — the site *is* the pitch. Blocking training crawlers guarantees Postr is never in the weights, so it is never the unprompted recommendation when a grad student asks an assistant what to use instead of PowerPoint. Bytespider is blocked because it has a documented record of ignoring disallow directives and offers no citation surface that returns traffic.

### Sitemap strategy

Three files. The index exists not for scale — Postr is nowhere near the 50,000-URL limit and will not be for years — but because the halves have different freshness requirements. Static routes change on deploy; gallery entries change whenever a user clicks Publish.

- `apps/web/public/sitemap.xml` — committed index, never changes.
- `dist/sitemap-static.xml` — written by `scripts/gen-sitemap.mjs` at build.
- `/sitemap-gallery.xml` → `api/sitemap-gallery.ts` Edge Function, `cache-control: public, s-maxage=3600, stale-while-revalidate=86400`, generated **from the indexability predicate** so it is a curated positive-signal set. Uses the anon key against the existing RLS policy — no service role, no new secret.

The 1-hour edge cache is the entire freshness mechanism. **Do not wire a Supabase webhook to a Vercel Deploy Hook** — a full rebuild per publish is a self-inflicted DoS that gains at most 59 minutes.

`lastmod` = `created_at`. `gallery_entries` has **no `updated_at` column** (verified in `20260410030000_gallery.sql`), which is honest since entries are effectively immutable. If editing is added later, add the column with a trigger *before* changing `lastmod` — an inaccurate `lastmod` is worse than none, because Google demotes the signal site-wide once it catches you. Omit `<changefreq>` and `<priority>` entirely; Google has ignored both for years.

Exclude unconditionally: `/s/*`, `/auth`, `/debug`, all auth-gated routes. A noindexed URL in a sitemap is a Search Console error.

Site names are domain-level and unsupported for subdirectories, so this block belongs on the home page only — which the shared `index.html` gives you automatically, and that is fine because Google confirms unsupported placements are inert.

**Ship no `potentialAction` / `SearchAction`.** Google retired the sitelinks searchbox rich result — announced October 2024, removed from results starting November 2024; the documentation page is deleted and `SearchAction` appears nowhere in the current Search Gallery (last updated 2026-06-15). There is no primary-source evidence it aids LLM parsing either. Entity disambiguation is `Organization`'s job, not `SearchAction`'s.

**2. Landing page — `WebApplication`.** No rich result without `aggregateRating`, and Postr has no review corpus — **do not invent ratings**, that is a spam violation. Its value is entity understanding: the `featureList` below is the highest-signal block on the site for an assistant answering "what free tool makes conference posters."

**3. Gallery entry — `CreativeWork` + `BreadcrumbList`**, injected by `api/shell/gallery.ts`. ## 7. Off-page & AEO

### What is solid

**LibGuide and undergraduate-research-office outreach** (Phase 4). This is the strategy; directories are housekeeping. A link on a university poster guide is worth more than every directory listing combined, because it is an editorial link on a high-authority `.edu` from exactly the right context. LibGuides also propagate — librarians copy each other's guides — so early wins compound. Two caveats: many LibGuides sit on parameterised URLs (`c.php?g=1222845&p=8976597`), so value them as qualified referral traffic and citation signals rather than PageRank; and the guides are visibly rotting (NYU's still recommends Gliffy and Lovely Charts and omits Canva and BioRender entirely; Yale's vendor list points at "MakeSigns," a company that now 301s to posternerd.com). Outdated guides with reachable named maintainers is the whole opening.

**Allow all AI crawlers** (§6). Free product, no content to protect, and blocking the search-index crawlers forfeits exactly the citations you want.

**The QR loop** — highest-leverage, cheapest item in this document. At a conference a printed poster is seen by hundreds of exactly the target audience in a context where they are actively thinking *"I have to make one of these."* An opt-in QR in the poster export resolving to the author's gallery entry turns every printed Postr poster into a physical acquisition surface with zero marginal cost and zero link-scheme risk. Make it small, tasteful and corner-placed so authors don't disable it on aesthetic grounds.

**The share moment.** After a successful gallery publish, one screen with: pre-written editable share text, a correctly-sized PNG, the citation line for their CV, and the embed snippet. The 30 seconds after publishing is the only moment the author is motivated to promote; every extra click loses most of them.

**Open-source the readability checker, not the editor.** The checker is the credential; the editor is the product. That unlocks an authority ladder unavailable to a SaaS: awesome-lists (hours, editorial links on github.io, heavily represented in retrieval corpora) → Zenodo DOI on release (days, makes it formally citable) → JOSS submission (months of review latency, but a CrossRef DOI produces Google Scholar presence, which produces citations in real papers' reference lists on publisher and `.edu` domains). JOSS acceptance is a reviewer judgement call on "obvious research application" and is not assured.

### What is speculative — say so out loud

**The "brand mentions beat backlinks 3-to-1" statistic is not usable.** Ahrefs' 0.664-vs-0.218 Spearman figure comes from a May 2025 dataset filtered to `DR > 40` with a keyword at 800+ monthly searches. That filter truncates the range of the *link* variables while leaving mention range intact, which mechanically deflates the link coefficients — the ratio is partly a sampling artifact. The authors call all their coefficients "moderate to very weak" and disclaim causation. It is Google-AI-Overviews-specific (the same signal correlates 0.15 with ChatGPT visibility), unstable across their own follow-ups (link-authority coefficients flip sign, -0.12 to 0.01), and **the sampling frame excludes Postr by construction**. Do not cite it. Keep third-party mentions, but justify them on referral traffic from where researchers actually are, and add one operational rule that settles it empirically: **when you earn a mention, ask for the link.**

**Do not elevate a dedicated link-buying campaign either.** Google's stated position is that links have not been a top-three ranking factor "for some time," and unlinked mentions do nothing for PageRank. Neither lever earns a standalone workstream at Postr's stage.

**GEO copy tactics carry no forecast.** The Princeton GEO paper's 22–41% figures measure a source's *share of an already-generated answer* with retrieval held fixed — the authors state in their own Limitations that they did not evaluate effects on search rankings. Two rigorous replications since contradict the tactics: C-SEO Bench (NeurIPS 2025) finds them "largely ineffective and often negative for document ranking," with retrieval rank dominating; SAGEO Arena (2026) finds body-only optimization *reduces* top-20 retrieval presence ~9% and final citation ~6% once retrieval and reranking are reinstated. Keep the tactics — specific numbers, cited sources, authoritative tone are simply good writing for a researcher audience — but attach **no number**, and do not let GEO-flavoured rewrites degrade the crawlable text, headings, or structural markup.

**`llms.txt`: 15 minutes, no more.** Ship one hand-written static file at `apps/web/public/llms.txt` linking the conference directory, the readability checker, the gallery index, and `/about`. Build no tooling, no per-route variants, no `llms-full.txt`. Justify it as cheap optionality and nothing else. The evidence: 97% of published `llms.txt` files received zero AI requests in a 137,210-domain sample; the largest fetch category is SEO audit tools; a 300k-domain model found removing the variable *improved* accuracy; exactly 1 of 94,614 AI citations came from one. **Do not write that Anthropic or Perplexity "support" or "honor" llms.txt** — no vendor documents consuming it. That belief traces to a category error: both vendors *publish* a Mintlify-generated `llms.txt` for their own docs sites, which SEO blogs restated as crawler support. Google states outright that Search, including its generative features, does not use such files.

**Most-cited-domain leaderboards contradict each other by an order of magnitude** — one sourced claim puts Reddit at ~40% of AI citations, another compilation of six studies covering 680M+ citations says the most-cited domain on any platform rarely exceeds 5%. Do not set KPIs against these figures or pay for tooling justified by them.

**"Made with Postr" badge — nofollow, brand-only anchor, opt-in, never a condition.** Google's spam policies name "keyword-rich, hidden, or low-quality links embedded in widgets that are distributed across various sites" and "exchanging goods or services for links." A distributed badge with a followed keyword anchor is a close match. Google's own remedy is qualification, and reporting suggests it auto-nofollows recognized widget links anyway, so the followed version likely buys nothing even before the risk. All four conditions required: (1) `rel="nofollow"` hardcoded in the embed snippet; (2) anchor is the brand only — never "free research poster maker"; (3) opt-in, off by default, trivially removable; (4) **never** condition any feature on displaying it. Built this way it is a brand-mention and referral play, which is the better version anyway. Frame it that way to stakeholders so nobody "optimizes" the anchor text later.

**Wikipedia: do not attempt.** WP:NSOFT requires multiple independent reliable sources; a founder-created article gets speedy-deleted and attracts durable COI scrutiny. An unsuccessful attempt costs the option permanently. **Wikidata** is a genuinely different and much lower bar — after the Zenodo DOI exists, create an item with `instance of` (software), official website, source repository, license, DOI, and disclose the affiliation on your user page. Costs an hour; expected value modest and unmeasured. Do it, do not oversell it.

### Content quality bar for Phases 2–6

This plan produces a lot of prose: 7 conference pages, ~18 size pages, a tool page, 3–4 comparison pages. Generated-feeling content is precisely what the scaled-content and helpful-content signals target, and academics are an unusually low-tolerance audience for marketing voice. Two standards, both borrowed from the OpenSEO repo and both cheap to apply:

- **Run the `deslop` pass on every published page.** It is a concrete catalog of AI writing tells — throat-clearing openers, binary contrasts ("Not X. Y."), self-posed rhetorical questions, tricolon abuse, bold-first bullets, em dashes, "it's worth noting," vague declaratives, invented concept labels. It ships with a 5-dimension scoring rubric (directness, rhythm, trust, authenticity, density; revise below 35/50). The skill lives at `.agents/skills/deslop/` in that repo and can be copied into `~/.claude/skills/` to invoke directly.
- **Traceable truth.** Every capability claim, number, and screenshot must be verifiable against the code or the live product before it ships. This is not a new rule for this project — it already caught a real error in the print flyers (a claim of "seventy slash commands" against 65 actually defined in `apps/web/src/poster/symbols.ts`). Applied here it means: the DPI claims on size pages must match what the export pipeline genuinely produces (§9 flags this as a real risk), the conference specs must carry a human-verified `sourceUrl` and visible `verifiedOn`, and the comparison pages must not describe features Postr does not have.

### KPI targets

**These are experience-based estimates for a zero-authority domain, not measurements.** The single biggest determinant is whether Phase 1 ships; if crawlers keep receiving an empty div, halve everything and delay it by a quarter.

| | Month 3 | Month 6 | Month 12 |
|---|---|---|---|
| Public routes indexed | 100% of static routes | + conference & size families | + majority of index-eligible gallery entries |
| Referring domains | 10–25 | 40–80 | 120–250 |
| of which `.edu` | 0–3 | 5–15 | 20–40 |
| Organic clicks / month | 0–50 | 200–800 | 2,000–8,000 |
| Head-term rankings | none | none | none |
| Long-tail rankings | none | first `[conference] poster template`, `48x36 poster template` | page one on a portfolio of conference + size long-tail |
| Branded search "postr" | ~0 | first measurable volume | meaningful |
| AI citations | 0 | first, iff the awesome-list / roundup work landed | occasional |

**Months 0–3 will feel like nothing is working, because for a brand-new domain it largely isn't yet.** That is normal and is not a signal to change strategy. The goal in that window is indexation, not rankings.

**What will not happen in year one:** page one for `research poster maker`, `poster maker`, or `scientific poster template`. Realistically 18–36 months, and only with sustained `.edu` link acquisition.

**Calibrate expectations on AI surfaces honestly.** The best causal evidence available (Agarwal & Sen, SSRN 6513059 — pre-registered randomized field experiment, n=1,065, Jan–Feb 2026) finds AI Overviews cut outbound organic clicks ~38–40% and raise zero-click searches from 54% to 72%. Pew's widely-quoted 8%-vs-15% CTR figure is observational and uncontrolled for query mix — Pew's own data shows AI summaries appear on 60% of question-word queries versus 8% of one-to-two-word queries — so lead with the RCT and treat Pew as descriptive colour. Quote either only with date and sample-frame attached; never as a bare stylized fact in public-facing Postr content. The implication for this plan is not to abandon search but that **being named in the answer matters more than ranking below it**, which is why the extraction-friendly page structure, third-party mentions, and the offline QR channel carry disproportionate weight.

## 9. Risks, open questions, and what we are explicitly not doing

### Needs the owner's decision before the relevant phase starts

1. **The analytics policy contradiction — blocks all measurement.** `apps/web/src/pages/Cookies.tsx` publicly promises, by name, that Postr runs no Google Analytics, Matomo, PostHog, or Plausible, and commits that if optional analytics are ever added, Postr will "update this policy, display a consent banner with equally-visible Accept and Reject choices, and refrain from setting any non-essential storage until you click Accept." Quietly breaking that is both a trust failure and a GDPR/Law 25 problem. Three honest options: **(a)** server-side only — Supabase + API logs + Search Console, no policy change, no banner, but no client referrer attribution; **(b)** cookieless first-party analytics that set no persistent identifier, rewrite the §4 bullet honestly — the ePrivacy Art. 5(3) consent requirement attaches to *storage/access on the device*, so a genuinely storage-free implementation can avoid the banner, but the named-tools bullet still must change (**recommended**); **(c)** full product analytics with a consent banner, highest fidelity but consent-gated data under-counts by a large and non-random margin, which corrupts exactly the attribution being built. **Decide before Phase 0 ships**, because the first-touch capture cannot be retrofitted.

2. **Does gallery publish consent cover public search indexing and text extraction?** The RLS policy was read; the consent copy in `PublishConsentModal` / `PublishGalleryModal` and the Terms were not. Phase 5's OCR/text-extraction step renders users' unpublished research as page content. If the consent language does not cover it, that step is blocked until the Terms are updated — and consent cannot be retrofitted after indexing.

3. **Author attribution on `gallery_entries`.** There is no author name, affiliation, ORCID, or homepage column (`20260410030000_gallery.sql:31-53`). Researchers share pages carrying their own name and institution because sharing is a credentialing act; an entry that does not name its author is a Postr asset, not an author asset, and nobody promotes it. Adding it is a privacy decision requiring an explicit opt-in checkbox, not an inference from the account. Blocks the gallery flywheel.

4. **Ship the react-router v6 → v7 security bump now, or defer?** Four open advisories, three unpatchable in v6. It is a days-scale change staying in declarative mode, with **zero** SEO value. It should not be held hostage to this plan's timeline in either direction. Stopgap if it slips: bump 6.30.3 → 6.30.4, which clears exactly one of the four.

5. **Keyword volume pre-flight — RESOLVED 2026-07-27.** Ran via OpenSEO `get_keyword_metrics`; full data and verdicts in §4.0. Outcome: size cluster ≈5,190/mo aggregate clears the threshold → Phase 3 keeps full scope; canva cluster cut entirely; `/chart-chooser` slug confirmed. Original spec follows for the record. No search volumes were measured in any research stream. **Preferred instrument: self-hosted OpenSEO via its MCP server (§8)** — `get_keyword_metrics` returns volume, difficulty, intent and trend for up to 700 terms in one call, which is strictly more than a bucketed range and makes the kill/keep call defensible rather than directional. It costs DataForSEO credits, so it is cheap-not-free. Free fallback: Google Keyword Planner with any Ads account returns bucketed absolute ranges (10-100, 100-1K, 1K-10K) with no ad spend — bucketed is the minimum granularity this decision needs. Google Trends and Bing Webmaster Tools are also free. Pull the size cluster and the top 3 conference terms, and **write the kill/keep threshold into this doc before building** (suggested: if the size cluster is not ≥1K-10K, cut Phase 3 to the 8 existing presets and stop). Exempt the conference×year cluster from this test — Keyword Planner uses trailing-12-month data, which genuinely understates year-suffixed terms — and gate it instead on a single hand-built pilot page measured in Search Console.

6. **Current `gallery_entries` row count and distinct-author count.** MOOTED by the 2026-07-27 gallery freeze (Supabase MCP is now callable if this is ever revisited). Original note: could not be queried (Supabase MCP requires OAuth, unavailable in a non-interactive session). If the gallery is already at hundreds of entries from many authors, Phase 5 moves earlier and the discipline-hub thresholds are already cleared. If it is single digits, Phase 5's hubs cannot ship at all this year.

### Explicitly not doing (YAGNI)

- **React Router framework mode / Next.js / Astro / TanStack Start / Vike.** Next.js is a 15–30 dev-day `'use client'` audit of the whole editor. Astro's hybrid split is technically excellent and organizationally wrong for one developer — two apps means two Tailwind configs and two copies of the `--ease-*`/`--dur-*` motion tokens, `PublicHeader`, `PublicFooter` and the brand swatch, and those **will** drift on exactly the surfaces prospective users see first.
- **`vite-react-ssg`.** Actively maintained, but its peers pin `react-router-dom: ^6.14.1` — welding Postr to an EOL router — and its own README now steers users to React Router v7's built-in SSG. It also requires converting `routes.tsx` to route objects, i.e. the same restructuring cost as the React Router path spent on a dependency the author is deprecating.
- **`react-snap` (last published 2022-05-15), `vite-plugin-prerender` (2022-09-05), `@prerenderer/rollup-plugin`.** Dead.
- **Dynamic rendering / user-agent sniffing.** Google explicitly deprecated it in 2022 as a workaround rather than a solution. The named risk is implementation drift — a prerendered copy silently diverging from the live app over months — and a divergent copy *is* how you back into an actual cloaking violation. Serve identical HTML to every client.
- **Prerender.io or any paid bot-serving service.** ~$90+/mo for a permanent per-request edge hop on a vendor-deprecated pattern.
- **A blog.** Competing with ~50 university LibGuides on informational intent from a zero-authority domain.
- **`SearchAction`, `FAQPage`, `HowTo`, `Product`, `Review`, `AggregateRating`, `ScholarlyArticle`, `Dataset` schema.** Reasons in §6.
- **`/gallery/conference/:x` and `/gallery/year/:y` as URLs.** Free-text facet explosion with a user-controlled URL space.
- **Generic paper-size conversion pages, `poster printing` content, Greek-symbol/table-border content.**
- **Wikipedia article. Directory blasts. Paid "dofollow guaranteed" placements.** G2/Capterra: claim the free profiles for brand control, invest nothing further — your users are students and postdocs who do not write B2B software reviews.
- **Deploy-hook-on-publish rebuilds.** The edge sitemap function makes them unnecessary.

### Other risks

- **Overclaiming DPI.** A 48×36 poster at 300 DPI is 14400×10800 px — far beyond safe browser canvas limits. If any size page implies Postr produces that raster, the export pipeline must actually deliver print-quality output (vector PDF, not a rasterized canvas). Overclaiming DPI on an SEO page the product can't honour is uniquely damaging here, because "72dpi print disaster" is the exact pain Postr positions against.
- **Wrong conference specs.** Two known data errors already exist in `GuidelinesPanel.tsx` (§3 Phase 2). A wrong board dimension gets someone's poster rejected. Every row needs a human-verified `sourceUrl` and a visible `verifiedOn`, and the model needs `orientation` and `unitSystem` — ECNP (portrait, metric) and SfN/APA (landscape, imperial) cannot share a preset shape.
- **`scifig.ai` is a content competitor, not just a product one.** It is already running exactly this conference-guide playbook competently — `/blog/sfn-poster-guidelines-and-template` is a 19-minute read citing eight official SfN sources with its product integrated throughout, and the set already covers ESMO, SITC, AHA, ASH, ASHG. Benchmark against that page, not against PosterPresentations. And assume the SERP resets when official bodies publish current-year dimensions — so build things that are durable to that reset (template and tool pages) rather than things that aren't (dimension explainers).
- **Automated paper→poster generation is commoditizing fast.** Paper2Poster (NeurIPS 2025) generates an editable .pptx poster from a PDF in under 5 minutes for ~$0.005, and has spawned a research line plus commercial entrants. Postr's moat therefore cannot be "makes a poster for you" — it has to be print correctness at 300 DPI, conference-spec compliance, figure legibility at physical size, and author/affiliation structure. That is reassuringly where the stated differentiators already sit, but it argues for leaning harder into correctness framing and away from convenience framing.
- **Gallery has no pre-publish moderation gate.** `gallery_entries_insert_own` grants INSERT to `authenticated`, and under anonymous-first auth every visitor is authenticated; `gallery_entries_public_select` makes the row publicly readable instantly. The 5/day rate limit is per-*session*, and a fresh anonymous user costs one API call. Moderation is entirely reactive via `/admin/gallery`. The indexation predicate is the mitigation — it gates *indexation*, not publication, preserving the anonymous-first promise while removing the SEO liability. Also sanitize `notes` on render (2,000 chars of free prose, currently unsanitized on this path) and emit any surviving link with `rel="ugc nofollow noopener"`.

## 10. Confidence notes

**High confidence, primary-source verified.**
- Googlebot fully renders JavaScript; AI Overviews and AI Mode are served from the same index with no additional technical requirements. Google deleted its JS caution in March 2026.
- Vercel checks the filesystem before applying `rewrites`, empirically confirmed against this deployment (`/version.json`, `/favicon.svg`, `/seeds/*` already win over the catch-all). Guaranteed only because `vercel.json` uses `rewrites`, not the legacy `routes` property.
- `cleanUrls` defaults false and is unset: `/logo-final.html` returns the 16KB file, `/logo-final` returns the 932-byte shell.
- `@react-router/dev@7.18.1` + Vite 8.0.8 + React 18.3.1: install, build, and prerender all pass, and prerendered HTML contains real per-route `<title>`/`<meta>`. Not a blocking risk if the runner-up is ever chosen.
- React Router v6 EOL 2026-06-17; four open advisories; three unpatchable.
- FAQ rich results removed May 2026; HowTo retired 2023; sitelinks searchbox retired Oct/Nov 2024. `WebSite` schema is *not* deprecated and drives the Site Name feature.
- SfN board = 6 ft × 4 ft (72 × 48 in) landscape, maximum not requirement, verified on sfn.org 2026-07-27, unchanged since at least 2014.
- **Live-measured against the production deployment on 2026-07-27** (`curl`, not inferred): Googlebot receives a 932-byte shell with `<title>Postr</title>` and an empty `<div id="root">`; `/robots.txt` and `/sitemap.xml` both return 200 `text/html`; `/this-page-does-not-exist`, `/wp-admin` and `/random/deep/path.php` all return 200 (unbounded soft-404 space); the apex redirect is **307, not 308**. These are the baseline facts §1 and §6 rest on and they are reproducible in one command each.

**Medium confidence — acknowledged uncertainty.**
- **AI crawlers do not execute JavaScript.** This is the entire justification for Phase 1's AI-citation half, and the whole evidentiary base is **one Vercel/MERJ study from December 2024** (GPTBot fetched JS in 11.5% of requests, ClaudeBot 23.8%, neither executed). Every 2026 article asserting it recycles that dataset with no fresh telemetry. Probably still true — no vendor has announced rendering, and per-fetch compute economics argue against it — but treat it as one aging measurement. **If it turns out to be wrong, Phase 1 does not collapse**: social unfurl bots not executing JS is definitional and not evidence-dependent, and that alone justifies the work. Re-verify with `curl -A GPTBot` against postr.sh after Phase 1 — that test is free and definitive.
- Directory-index resolution (`/about` → `dist/about/index.html`) under this specific `vercel.json` **could not be verified** — the current deployment contains no subdirectory with an `index.html`, and Vercel's docs do not state it explicitly. This is the one behavior that must be smoke-tested on a preview deployment before Phase 1 is considered done. Ship a throwaway `dist/__smoke/index.html` and assert `size_download != 932`.
- JOSS accepting a figure-legibility linter as having an "obvious research application" is a reviewer judgement call. If rejected, Zenodo + awesome-lists still work but the credential ladder loses its top rung.
- LibGuide conversion assumptions — that librarians respond to named-human emails, that late-August/early-January are the refresh windows, that ~30 qualified guides/week is sustainable — are reasoned from how those roles and the academic calendar work, not from measured outreach data. Validate the seasonality claim with a small test batch before committing a quarter to it.

**Low confidence / explicitly unmeasured.**
- **Winnability judgements in §4 remain inferred from SERP composition,
  content supply, and product fit.** Demand estimates are now measured for the
  three pre-flight sets in §4.0–§4.0.2; no measured row is correctly treated
  as below-floor, not zero. See resolved open question 5.
- **Ranking observations in the research came from Brave's index, not Google's.** A cross-check against a Bing-derived index materially reordered the SfN cluster (sfn.org took #1 and #3; scifig.ai fell to #4). No Google position can be inferred from any of it. An incognito browser check is *not* the fix — incognito removes cookie and history personalization but retains IP geolocation, so it is not a neutral SERP either. Post-launch Search Console impression data is the only authoritative position source; no third-party rank claim substitutes for it, especially after Google deprecated `&num=100` in September 2025.
- **AI Overview presence on Postr's specific query set is unmeasured.** No live SERP was observed, and a single observation would be unreliable anyway — measured day-to-day source overlap between consecutive days is only 34–42%, and AIO prevalence swung roughly 4× during 2025. Mandate quarterly re-checks with repeated sampling; never a single observation.
- **All KPI ranges in §8 are estimates**, calibrated pessimistically on purpose. Single-site variance is large.
- The assumption that 48×36 and A0 remain dominant standards. Some societies have been moving toward "better poster" formats and portrait-only or ePoster requirements; that was not investigated. If a major target society has changed format, a spec page could be confidently wrong — which is the worst failure mode for this content type.
- The ~40–60 conference-page ceiling assumes most major conferences publish guidance specific enough to clear the four-part quality bar. If most publish only vague guidance, the honest ceiling is closer to 15–20, which materially shrinks Phase 2.
