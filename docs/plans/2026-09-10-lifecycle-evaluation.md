## 1. Verdict — is the money path safe to market against today?

**No.** The free path (guest editor, free watermarked PDF, `/chart-chooser`) is sound enough to send traffic to. The paid path is not: four confirmed P0 defects sit in `apps/api/src/billing.ts` and `apps/web/src/pages/Profile.tsx`, and the self-serve refund the Terms advertise most likely cannot execute at all.

Confirmed P0 (money / access / data loss):

1. **Term refund never cancels the Stripe subscription** — the refunded customer is charged CA$18.99 again in 4 months and any later `customer.subscription.updated` (including the cancel-at-period-end the Terms tell them to do) re-grants the term. After the refund the Profile hides "Manage subscription" and offers "Get a subscription", which opens a *second* live subscription. `billing.ts:1103-1115, 1229-1235`.
2. **No duplicate-term guard and term revoke keyed on user id only** — an active subscriber can buy a second term from `/pricing` or any `/auth?plan=term` link; a terminal event for the older sub then revokes the newer paid one. `billing.ts:200-268, 857-866` (contrast the add-on guard at `:825-833`).
3. **Account deletion orphans a live subscription, silently** — `delete_own_account` only deletes `auth.users`; renewal webhooks resolve the deleted uuid from subscription metadata, update 0 rows and return 200. Stripe keeps billing; Postr holds no mapping to find or refund it. `supabase/migrations/20260410000000_delete_own_account.sql:15`, `billing.ts:879-903, 697-711`.
4. **Profile "Sign up with Google" orphans the guest's posters** while the card promises they will be linked (`signInWithOAuth`, not `linkIdentity`). `Profile.tsx:307-313, 361-364`.

Confirmed high items that make the paid promise false in practice: self-serve term refund expands a field Stripe removed in Basil (likely 500/409 on every click, `billing.ts:1076-1085`); `charge.refunded` reconciliation is dead / misclassifies term refunds as pack refunds (`billing.ts:927-930, 961`); paid PPTX/LaTeX still contain the Postr logo picture despite "no watermark" (`export/pptx/writer.ts:648-666`); a pack holder can export without limit while staying on the Export tab (`EditableExportButtons.tsx:173-179`); the EU withdrawal waiver is never collected on the `/pricing` path nor recorded anywhere (`billing.ts:232-251`).

Legal before any push: Privacy Policy predates billing, contradicts the Cookies Policy on analytics, omits Stripe and OpenAI, and still has a "region to be confirmed" placeholder (`Privacy.tsx:16, 165-172, 298-300`). Terms §7.2 promises a checkout acknowledgement that does not exist.

Marketing-claim check: **no standalone plot-checker route exists in this worktree** (`routes.tsx:121-199`); `Landing.tsx:176-183` already promises one on mobile. The readability check lives inside the editor Figure tab only.

Minimum bar before the push: fix P0-1..P0-4, H-10/H-11 (refund path), H-3 (logo in paid exports), H-8 (credit refresh), H-1 (privacy notice), H-5 (password reset), H-2/H-6 (guest sign-in orphan + false "account created" toast); run the §4 dashboard/sandbox checklist, in particular Manual Linking, webhook events + API version, Managed Payments approval, Render `APP_ORIGIN`/`CORS_ORIGINS`.

What is solid: webhook mounting/signature/idempotent pack grant, DB guard trigger + RLS + RPC hardening, atomic credit consume, consent unchecked by default, in-place guest→email conversion on `/auth` (manual-test-flows §1b is fixed), SEO/prerender plumbing, cookieless analytics, `/chart-chooser` is genuinely client-only.

### P0 — launch blockers (money / access / data / legal) — all CONFIRMED

**P0-1. Term refund never cancels the Stripe subscription; refunded user is re-billed and re-granted** — critical · 0.85 · not in docs.
`refundTerm` calls `stripe.refunds.create` then `recordRefundAndRevoke`, whose term branch writes only `plan='free', plan_expires_at=now()`; `stripe_subscription_id` and `subscription_status='active'` stay. `grep subscriptions.cancel|subscriptions.update|cancel_at` over `billing.ts` returns nothing (only four `subscriptions.retrieve`). Refunding an invoice does not cancel a Stripe subscription, so the next cycle bills again and `handleSubscriptionChange`/`handleInvoicePaid` → `advanceTermAccess` re-grants because the forward-only compare sees `now()` < period end. The cancel-at-period-end the Terms recommend (`Terms.tsx:235-240`) fires `customer.subscription.updated` status active → re-grant to period end. After the refund `usePlan.hasActiveTerm` is false, so Profile shows the free panel with no "Manage subscription" button and a "Get a subscription" CTA → `/pricing` → `/auth?plan=term` → second live subscription. Same gap in the webhook term-refund branch.
Files: `apps/api/src/billing.ts:1103-1115, 1229-1235, 686-696, 845-854, 962-971`; `apps/web/src/pages/Profile.tsx:1110, 1155-1206`. Verified by three independent stage verdicts.
Impact: money re-taken from an exited customer under MoR (dispute exposure); wrongful re-grant; UI-reachable double subscription.
Fix: cancel the subscription in `refundTerm` and in the term branch of `handleChargeRefunded` (`stripe.subscriptions.cancel(id, {prorate:false})` or `update({cancel_at_period_end:true})` per policy); write `subscription_status='canceled'` and clear `stripe_subscription_id` in the same revoke UPDATE; guard `advanceTermAccess` so a stored terminal status is never re-activated by the same sub id; say in the success copy that the subscription is cancelled. Unit test "term refund cancels the subscription". Sandbox: buy term → refund → advance test clock 4 months → no invoice, plan stays free.

**P0-2. No duplicate-term guard; term revoke matches on user id, not subscription id** — critical (paywall verdict) / high (lifecycle verdict) / medium (fulfillment verdict, edge-only view) · 0.8 · not in docs.
`create-checkout` reads only `req.body.sku` and never `users.plan/plan_expires_at` before `sessions.create`; `PricingSection.tsx:82` hard-links "Get the term" to `/auth?plan=term` with no `usePlan` import; `Auth.tsx:158-190` auto-starts checkout for any permanent session. So an active subscriber (or a refunded one per P0-1) opens a second live subscription. `advanceTermAccess` overwrites `stripe_subscription_id`/`stripe_customer_id` with the newest sub; a later `.deleted`/terminal event for the older sub resolves through `findUserIdForSubscriptionEvent`'s `metadata.user_id` fallback and the terminal branch `.update({plan:'free',...}).eq('id', userId)` revokes the newer paid term. The add-on branch already guards with `.match({review_addon_subscription_id: sub.id})` and has the test (`billing.test.ts:595`); the term branch has neither. Symmetric: a redelivered "active" for an old sub re-grants after a real cancel.
Files: `apps/api/src/billing.ts:200-268, 698-707, 857-866, 825-833, 879-903`; `apps/web/src/components/PricingSection.tsx:81-82`; `apps/web/src/pages/Auth.tsx:158-190`.
Impact: double recurring charges; paying user loses access on cleanup. On the plain cancel→expire→re-buy sequence it cannot trigger; it becomes likely combined with P0-1 or a failed webhook delivery.
Fix: in `create-checkout` refuse `sku=term` when `plan='term' && plan_expires_at>now` (409 `already_subscribed`; client shows "You already have an active term"); hide/disable the term CTA on `/pricing`, the paywall and the `/auth?plan=` resume when `hasActiveTerm`; revoke only when `stripe_subscription_id = sub.id`; on the active path advance only when the event's sub id equals the stored one or the stored one is null/terminal; add the stale-event test for the term.

**P0-3. Deleting an account orphans a live Stripe subscription — silently** — critical (end-of-life verdict) / high (lifecycle verdict) · 0.9 · **manual-test-flows §18 "Stripe orphan" — still open, unchanged**.
`Profile.tsx:283` calls `rpc('delete_own_account')`; the function is one statement, `delete from auth.users where id = auth.uid()` (`20260410000000_delete_own_account.sql:15`), cascading `public.users` (`20260408000000_users.sql:13`) and with it `stripe_customer_id`/`stripe_subscription_id`. No Stripe call anywhere in the delete path; the edge function on disk (`supabase/functions/delete-account/index.ts:59-62`) is unreferenced and also only calls `deleteUser`. Danger Zone and ConfirmModal (`Profile.tsx:703-720, 762`) show no active-subscription warning even though `plan.hasActiveTerm` is on the page (`:50, 1110`). Correction to the lifecycle trace: later `invoice.paid`/`customer.subscription.*` do **not** 500 — `findUserIdForSubscriptionEvent` returns the deleted uuid from subscription metadata (`billing.ts:900`), the UPDATE matches 0 rows with no error, and the webhook answers 200. `handleChargeRefunded` returns silently (`:946`). A re-signup gets a fresh row with null `stripe_customer_id`; `/billing/portal` 409s (`:413-417`); a new checkout creates a second customer/subscription (no `customer:` param, `:236-262`).
Impact: CA$18.99 every 4 months to a non-existent account until the user cancels via Link/Stripe receipts or dunning fails the card; Postr cannot find, refund or reconcile it; disputes land on the MoR account. Applies to `review_addon` too.
Fix: block deletion (or require a cancelled status) while `subscription_status` is non-terminal, or move deletion behind an API route that `stripe.subscriptions.cancel`s (and deletes the customer) before `deleteUser`; make the webhook treat a resolved-but-missing user as an error (500/alert) rather than a 0-row update. Delete or document the unused edge function (`docs/feature-graph.md:4903` says it is the deletion mechanism).

**P0-4. Profile "Sign up with Google" orphans the guest's posters while promising to link them** — critical (guest-editor verdict) / high (conversion verdict) · 0.9 · **§7 — still open; the doc's diagnosis ("relies on same-email auto-linking; verify Manual Linking") is wrong — it orphans regardless**.

An anonymous user has no email, so Supabase same-email linking cannot apply. `AuthGuard.tsx:17-22` lets guests reach `/profile`; the avatar link is in the dashboard and public header (`Home.tsx:189`, `PublicHeader.tsx:194`). Impact: data loss on a path the UI explicitly recommends. No test covers Profile (`pages/__tests__` has only `Auth.audit.test.tsx`).
